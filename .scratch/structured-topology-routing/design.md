# 结构化拓扑与混合路由设计

状态: 第二阶段已验收

## 目标

主要用户路径是通过 Python 和 NetworkX 构造 `NetworkSimulationGraph`，再调用一个结构化
case 运行接口。用户只描述真实节点、端口和连接，不需要为了启用规则路由而声明 Clos、
FullMesh、pod、leaf 或 spine 等角色标签。工具自动规范化物理图、提出结构候选并独立验证；
只有验证通过的路由查询项才使用规则路由，其余项保留表路由。

JSON/YAML 是同一 NetworkX 编译路径的可选声明式适配层，适合不想编写 Python 的用户；
它不是第二套结构发现或路由实现。现有 CSV case 继续作为独立支持的输入路径。

现有表路由、手工路由和自定义 path finder 保持可用。JSON/YAML 路径直接作为仿真
输入，默认不把内部编译结果写入磁盘，也不要求内部使用 CSV；内部传递格式按效率和边界选择。
用户显式请求诊断导出时，才输出对应 CSV 供检查。自定义拓扑路径与 JSON/YAML 路径可以
同时存在。

## 已确认的领域边界

- 结构只有“已验证”和“未验证”，不使用置信度决定是否启用规则。
- 一个物理节点可以同时属于多个结构视图，例如内部二维 Dimension FullMesh 和外部 Clos
  平面。
- 混合路由按“当前节点 + 目的节点 + 目的 UB 端口”划分归属。
- 一个路由查询项的最短和非最短候选端口由同一来源完整返回，不合并规则与表的结果。
- `RoutingKey` 保留现有含义，不用它命名上述归属单位。
- 当前 metric 只区分最短候选组和合并后的非最短候选组。第一阶段验证这两个集合，不声称
  保留数值 metric 的完整语义。

## 输入与内部处理

```text
Python + NetworkX ----------------\
                                  -> 物理拓扑图 -> 结构候选 -> 独立验证 -> 路由表示
JSON/YAML -> NetworkX 适配器 -----/                                  |-> 表路由
                                                                     |-> 规则路由
                                                                     `-> 混合路由
```

物理拓扑图是内部内存对象，必须保存：

- 节点 ID 和 host/switch 类型；
- 每条独立物理链路的两端节点和端口；
- 并行链路，不得在验证前丢失为一条简单边；
- 带宽、时延、edge count 及参与路由决策的属性；
- 稳定的原始节点、边和端口映射。

JSON/YAML 中的拓扑内容由四个可以组合的部分构成：

- `nodeGroups` 批量定义同类节点及数量；
- `groupConnections` 处理 FullMesh、All-to-All 和一一连接等单层批量连接；
- `layeredConnections` 配置任意层数、任意平面数以及层间连接；
- `explicitConnections` 逐条指定节点、端口和链路属性，可补充端口外扩、不规则连接，也可
  独立描述小型任意拓扑。

大规模规则部分应使用 `groupConnections` 或 `layeredConnections`，不要求逐条列出物理
链路。两者只是构造物理图的指令，不能直接证明路由结构；展开结果仍必须经过同一套自动
发现和独立验证。

每个 `layeredConnections` 项必须声明正整数 `planeCount` 和有序 `layers`。层通过数组序号
引用，不使用固定角色名；`planeMode: shared` 表示同一批节点供所有平面使用，
`planeMode: separate` 表示不同平面使用不同节点。`connections` 通过 `betweenLayers: [a, b]`
连接任意两个不同层，允许跨层连接，并用可选的 `parallelLinks` 表示每对端点之间的并行
物理链路数。

Python builder 或 JSON/YAML 是结构化编译的用户输入和事实来源。工具将验证后的结果原子写入
case 目录中的 `structured_topology.txt`；该文件是可重复运行的正式仿真输入，不是用户维护的
第二份拓扑源。诊断 CSV 是编译结果的可选快照，不得被默认运行重新读取。

Python 用户通过工具子模块提供的
`prepare_structured_case(graph, case_path, routing_mode="mixed")` 准备 case 并退出。
`scratch/ns-3-ub-tools/prepare_structured_case.py` 负责加载 NetworkX builder 或 JSON/YAML
适配器。`scratch/run_structured_topo_case.py` 只读取已准备的 case 目录、启动
`ub-quick-example` 并返回仿真退出码，不导入 NetworkX，也不执行结构发现或路由编译。

拓扑 JSON/YAML 只描述节点、端口、链路和链路属性，不包含表、规则或混合路由选择。
路由表示由准备命令的 `--routing-mode=table|rule|mixed` 选择，使同一拓扑输入可以准备三种
表示的对照 case。准备命令默认使用 `mixed`；`table` 和 `rule` 需要显式指定。拓扑内容哈希
和路由设置分别参与缓存键，不把运行选择混入拓扑身份。

输入顶层必须包含 `version: 1`。该值只表示结构化拓扑文件格式版本，不表示仿真 case 或
拓扑内容的修订号。解析器必须拒绝缺失、类型错误或不支持的版本，不能按最接近版本猜测。

每条 `explicitConnections` 记录必须通过 `group + index + port` 显式给出两个连接端点。
`group` 是 `nodeGroups` 中的组名，`index` 是从零开始的组内序号。节点的 `portCount` 可选：
省略时按该节点使用的最大端口号加一推导；显式填写时必须大于所有已使用端口号，用于保留
未连接端口。第一阶段不增加独立端口列表；内部端口、外部端口和多平面端口都由连接端点
表达。只有以后出现逐端口独立属性且不能放在连接上的需求时，才重新评估独立端口对象。

端口分配先保留 `explicitConnections` 中指定的端口，再按 `groupConnections` 和
`layeredConnections` 的声明顺序处理批量连接。批量连接可以分别限制两端可用端口范围；
指定范围时只能在范围内分配，容量不足必须报错，不得借用范围外端口。未指定范围时，按
节点当前最低空闲端口确定性分配。任何端口重复占用、负端口号或超出显式 `portCount` 都
必须在启动仿真前报错。

用户输入不要求计算全局节点 ID。编译器按 `nodeGroups` 声明顺序和组内 `index` 确定性地
生成无重复的连续内部 `nodeId` 范围 `0..N-1`，以复用现有按节点 ID 索引的数据结构。同一
输入必须产生同一映射，但结构发现不得从组名、ID 范围、声明顺序或命名模式推断拓扑语义。
诊断导出必须包含 `group + index -> nodeId` 映射。

节点的 `allocationDelay` 和 `forwardDelay` 是两个独立字段：前者表示交换分配周期，后者
表示入端口处理时延。新的 JSON/YAML 路径不得沿用旧四列 CSV 将 `forwardDelay` 解释为
allocation delay 的兼容行为，也不得在二者之间回退或复制值。

输入可以在 `defaults.node` 中统一声明 `allocationDelay` 和 `forwardDelay`，在
`defaults.link` 中统一声明 `bandwidth` 和 `delay`；具体节点或链路上的同名字段覆盖对应
默认值。解析完成后，每个节点必须同时有两个时延值，每条链路必须有带宽和链路时延；缺失
时在启动仿真前报错，不读取隐藏的 C++ 默认值。这样同一输入不会因运行时默认值变化而改变。

结构化入口允许通过 `--path-finder path/to/routes.py:function_name` 选择一个可选的自定义
path finder。默认仍使用 `nx.all_shortest_paths`。自定义函数沿用现有工具接口，签名为
`function(graph, source, destination)`，返回节点 ID 路径的可迭代对象；它生成第一阶段用于
比较的完整基准路由。函数文件内容、函数名和调用参数必须进入缓存键。`mixed` 只有在规则
结果与该基准逐查询项等价时才可替换表项，不能假设自定义 path finder 仍遵守标准最短路
公式。第二阶段也只能对已明确支持的 path finder 直接生成规则，其他自定义函数继续走基准
表或缓存路径。

现有 `NetworkSimulationGraph` 可以继续使用 `nx.Graph + edge_count` 作为公开 API。规范化步骤
在 `build_graph_config()` 分配端口后产生保留独立链路的内部视图，不要求用户改用
`MultiGraph`。

## 结构发现与验证

当前专用识别器：

- 一维 FullMesh；
- Ring、Mesh、Torus、ND Dimension FullMesh 及其混合维度；
- 两层 Clos；
- 多个独立 Clos 平面；
- Clos 顶层交换机的端口外扩边界；
- 经典平衡 Dragonfly；
- pair-design 关联网络；
- 同一批节点上的内部结构和外部结构组合。

维度结构不为 Ring、Mesh、Torus 和 ND Dimension FullMesh 分别建立互不相关的
拓扑模型，而是统一为 `dimension-network`。每个维度只声明一种简单连接关系：

```text
line       相邻坐标值连接
ring       相邻坐标值连接，并连接首尾
fullMesh   同一维度上的所有坐标值两两连接
```

节点由固定长度坐标标识；一条结构边只允许改变一个维度。只有一个 `ring` 维度时就是 Ring；
全部是 `line` 时是 Mesh；全部是 `ring` 时是 Torus；全部是 `fullMesh` 时是 ND Dimension
FullMesh。混合维度也是同一个模型，例如一维 `ring` 加一维 `fullMesh`。维度顺序不作为用户
标签，而由识别器恢复后规范排序；相同大小、相同连接关系的维度允许存在多个等价坐标映射。

Dragonfly 作为分层结构单独处理。第一版只接受经典 Dragonfly：

- 路由器可划分为大小相同的组；
- 每组内部路由器两两直连；
- 任意两个不同组之间恰好有一对全局相邻路由器，该路由器对可以有并行物理链路；
- 每台路由器具有相同数量的全局链路；
- 终端只归属于一台组内路由器，每台路由器的终端数量相同并由物理图推导；
- 组内、组间和终端链路的端口及并行数量都回到物理图验证。

“只归属于一台路由器”限定在一个 Dragonfly 结构内。同一终端可以同时属于内部维度网络，
也可以分别连接多个独立 Dragonfly 平面；共享节点允许，物理链路所有权不能重叠。

Dragonfly+、随机全局布线、组间多链路、UGAL 和 Valiant 路由不借用 `dragonfly` 名称。它们
在连接不变量或路由语义明确后作为独立变体加入。第一版 Dragonfly 规则只证明当前默认
metric 下的最短路径候选；非最短自适应路由继续使用自定义 path finder 和表路由。

颜色细化、商图、社区或图哈希以后可以用来提出候选，但不能直接证明结构成立。识别器输出
候选坐标、节点角色、结构边和边界；独立验证器负责：

1. 展开候选结构；
2. 比较节点双射；
3. 比较每条链路、两端端口、并行数量和路由相关属性；
4. 检查一条物理边只有一个结构视图负责；
5. 比较规则与基准表的最短、非最短候选端口集合。

缺边、增边、换边或属性不兼容只会使受影响部分未验证。已验证的独立区域仍可使用规则，
未验证查询项保留表路由。

## 第一阶段：正确性

第一阶段允许生成完整基准表：

```text
完整表路由
  -> 发现并验证结构
  -> 逐路由查询项比较候选端口
  -> 删除已由规则负责的表项
  -> 安装共享规则 + 本地端口组 + 剩余表项
```

运行时保持 `UbRoutingProcess::GetOutPort()` 为外部入口。内部先调用规则路由的尝试查询；
只有规则明确负责整个查询项时才返回候选，否则走现有表路由。最终 HASH、packet spray 和
ADAPTIVE 端口选择保持不变。

内部缓存可以按拓扑、端口、metric、路由设置和编译器版本的内容哈希复用验证结果。缓存
不是用户输入，也不是中间 CSV。第一阶段首次遇到一个缓存键时生成完整基准表；缓存命中
时直接复用已验证的规则和剩余表，不重新生成基准表。缓存失效时仍会重新生成完整基准表。
完全规则覆盖时，第一阶段冷启动的基准表只用于验证并在安装前丢弃，运行时表为空；部分
覆盖或无规则覆盖时，基准表还提供需要保留的表项。

第一阶段验收必须覆盖：

- 当前 4 x 4 Dimension FullMesh；
- 当前两层 Clos；
- 内部 Clos 加交换机端口外扩；
- 内部 Dimension FullMesh 加多平面 Clos；
- 并行链路和多目的端口；
- 打乱连续节点 ID 的拓扑角色分配、节点声明顺序和边顺序；
- 缺边、增边、换边和属性变化反例；
- 表、规则、混合三种表示的候选端口逐项等价；
- 手工路由和自定义寻路无法证明时保持表路由。

第一阶段完成报告必须明确：冷启动和峰值初始化内存仍受完整基准表限制，并宣布进入第二
阶段性能优化。只降低运行期常驻路由内存不代表整体完成。

## 第二阶段：性能

第二阶段在新拓扑或缓存失效时也不生成完整基准表，直接从已验证结构生成共享规则和未覆盖
表项。必须对比表路由和第一阶段混合路由，测量：

- 冷启动时间；
- 重复启动时间；
- 峰值初始化 RSS；
- 仿真运行期路由常驻内存；
- 路由查找延迟；
- 规则覆盖率和剩余表项数量。

第二阶段实现使用每个目的节点一棵最短路 DAG 直接产生候选端口，不枚举全部最短路径，也
不物化完整基准表。连续目的节点具有相同候选端口时会合并为范围规则；规则段内还会利用
“精确规则优先于范围规则”，选择默认范围并为少量不同目的生成精确例外。缺失目的和表路由
负责的目的会切断规则段。自定义 path finder 保留第一阶段完整基准路径，因为工具不能假设
任意用户函数满足标准最短路性质。

第二阶段验收结果见 `stage2-report.md`。1024-NPU 实图的 9,427,968 个路由查询项压缩为
40,704 条规则记录和 31,744 个本地端口组，不生成表项。64-NPU 实际
仿真子进程峰值 RSS 相对全表下降约 7.4%。逐包查找仍与表路由处于同一数量级；范围规则
比表或精确规则慢约 2 至 3 ns，因此主要收益是避免全表生成和降低路由常驻内存，而不是
宣称所有查询都会更快。

后续纯坐标/分组规则把完整安全结构直接编译为拓扑规则，exact/range 只保留为部分结构的
回退。1024-NPU 1DPOD 当前由 128 个组内 FullMesh 和 8 个带本地/共享 upper 的分层网络
生成 136 条规则；全部 9,427,968 个查询项已与逐目的最短路对齐。无内存跟踪的离线生成由
17.98 s 降至 1.37 s，完整输入协议体由 162,121,150 B 降至 789,816 B。C++ 在线查找仍是
计算换内存：拓扑规则约 36.63 至 172.23 ns，表查找约 4.50 ns。完整结果见
`topology-rule-report.md`。

## 原型结论

可丢弃原型已证明专用识别器加独立验证器可以覆盖上述核心组合，不依赖连续节点 ID 或边
插入顺序。端口外扩案例自然形成部分规则覆盖；破坏性反例不会被完整采用。原型仍使用
all-pairs shortest paths，只用于确认设计，不进入生产实现。
