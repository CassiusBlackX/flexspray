## 结论

第二阶段完成了默认最短路下的直接规则生成和 C++ 规则查询优化。用户可以直接在 Python 中
用 NetworkX 构造 `NetworkSimulationGraph`，调用 `run_structured_case()`；工具自动发现和
验证结构，再选择规则或必要表项。用户不需要声明 Clos、leaf、spine、pod 等内部标签，也
不需要生成中间 CSV。

默认 `mixed` 路径不再枚举全部最短路径，也不再为了验证而生成完整路由表。大规模规则图
能够显著降低路由生成时间、输入体量和常驻内存；逐包查找与原表路由处于同一数量级，不把
查找本身描述为主要加速来源。

## 使用路径

Python builder 返回工具现有的 NetworkX 图对象：

```python
from net_sim_builder import NetworkSimulationGraph


def build_topology():
    graph = NetworkSimulationGraph()
    # 使用 add_netisim_host/add_netisim_node/add_netisim_edge 构造真实拓扑。
    return graph
```

仓库入口直接运行：

```bash
python3 scratch/run_structured_topo_case.py \
  path/to/topology.py:build_topology \
  --case-path scratch/2nodes_single-tp
```

默认路由模式是 `mixed`。`table` 强制使用完整表；`rule` 要求所有查询项都能由已验证规则
负责，否则启动前报错；`mixed` 对已验证部分使用规则，对其余部分自动生成表项。JSON/YAML
输入和原 CSV case 是并列支持的路径。只有指定 `--export-dir` 时才输出诊断 CSV。

## 直接生成方式

默认最短路编译按目的节点构造一次最短路 DAG，从 DAG 直接得到每个当前节点的候选端口。
工具在物理图和已验证规则图上比较同一查询项；候选集合相同才交给规则负责。相邻目的节点
具有相同结果时先合并为范围规则；连续规则段内还可以选择一个默认范围，并用精确规则覆盖
少量例外。规划器先最小化记录数，再减少实际命中范围规则的查询数。缺失目的或表路由负责
的目的会切断规则段，不会被默认范围跨过。

自定义 path finder 仍走第一阶段的完整基准和缓存路径。任意用户函数可能实现非最短路、
约束路由或其他语义，不能用标准最短路 DAG 代替。

## 规模结果

以下均为冷缓存、默认最短路的当前代码实测：

| 拓扑 | 节点 | 链路 | 查询项 | 精确规则 | 范围规则 | 表项 | 协议体 | 冷编译 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| UBX 16-NPU | 20 | 88 | 880 | 112 | 96 | 0 | 6,933 B | 0.0049 s |
| 1DPOD 64-NPU | 176 | 1,248 | 36,288 | 960 | 1,344 | 0 | 89,811 B | 0.139 s |
| BST Fano | 21 | 28 | 112 | 48 | 22 | 0 | 2,577 B | 0.0013 s |
| 1DPOD 1024-NPU | 2,336 | 19,968 | 9,427,968 | 15,360 | 25,344 | 0 | 1,755,673 B | 35.39 s |

同一轮 64-NPU 测量中，完整表冷编译为 0.454 s、36,288 条表项和 611,117 bytes 协议体；
mixed 为 0.134 至 0.139 s，快约 3.4 倍，路由记录减少约 93.7%，协议体减少约 85.3%。
UBX 小图的协议体从 13,704 bytes 降至 6,933 bytes。

1024-NPU 原完整路由表约 146 MB、9,427,969 行（含表头）。直接生成得到 40,704 条规则
记录，记录数相对 9,427,968 个查询项减少约 99.57%；完整拓扑和路由协议体约 1.76 MB。
该次 Python 编译进程峰值 RSS 为 138,100,736 B，没有在内存中建立 9.4M 项基准表。

相对只合并相同连续段的编译器版本，exact-over-range 在 64-NPU 上减少 48 条范围规则和
829 B 协议体，在 1024-NPU 上减少 768 条范围规则和 16,000 B 协议体。UBX 没有适合该
变换的候选序列，因此结果不变。64-NPU 中规划器本身约 4.7 ms，占 134 ms 冷编译的约
3.5%；冷编译主耗时仍是结构识别和逐目的最短路 DAG。1024-NPU 两个版本的单次冷编译
时间分别为 27.66 s 和 35.39 s，不能据此声称该记录优化带来冷编译加速。

## 运行时内存与查找

64-NPU 使用相同拓扑、workload、`--stop-ms=1` 和独立冷进程测量：

| 模式 | 仿真子进程峰值 RSS | 路由记录 |
| --- | ---: | ---: |
| table | 68,468,736 B | 36,288 条表项 |
| mixed | 63,389,696 B | 2,352 条规则、0 条表项 |

真实仿真峰值 RSS 下降约 7.4%。该数字还包含节点、链路、协议栈、任务和 trace 等非路由
内存，所以不会与路由记录减少比例相同。该 RSS 数据对应优化前的 2,352 条规则；当前编译
结果为 2,304 条，尚未用独立仿真进程重测 RSS。64-NPU 编译对象的 `tracemalloc` 测量约为
当前 1.87 MB、峰值 3.16 MB。

500 万次查询微基准的三次结果范围：

| 查询表示 | 单次延迟 |
| --- | ---: |
| table | 约 6.6 至 7.8 ns |
| exact rule | 约 6.6 至 7.5 ns |
| range rule | 约 8.9 至 10.7 ns |

精确规则与表路由基本同量级。范围规则因分组后二分查找慢约 2 至 3 ns，但换来了大幅记录
压缩。第二阶段的主要收益是避免全表生成、降低路由输入和常驻内存，不是逐包查找加速。

## 正确性

- Python 工具测试 57 项通过。
- C++ `unified-bus-structured-routing` 通过，覆盖 stdin v2、CSV 范围规则、精确规则覆盖范围
  规则、非法协议和非法端口。
- UBX 的 880/880、64-NPU 的 36,288/36,288 路由查询项与旧表一致。
- 1024-NPU 的结构拥有全部 19,968 条物理链路；442/442 个受控样本同时与逐路径枚举和旧
  完整表一致。直接编译覆盖 9,427,968 个查询项，但没有重新载入完整旧表作为内存基准。
- NetworkX、JSON/YAML、诊断 CSV、原 CSV case 和结构化仿真 smoke 均保持可用。

## 限制

- 自动识别当前覆盖二维 Dimension FullMesh、直接交换、两层及多平面 Clos，以及这些结构
  的组合和端口外扩。未知或不规则部分在 `mixed` 中自动回退到表路由。
- 当前 metric 只保留最短候选组和合并后的非最短候选组，不承诺保留任意数值 metric 的
  完整语义；代码中保留了这一限制说明。
- exact-over-range 依赖运行时“精确规则先于范围规则”的既有优先级。当前优化只在相同
  `(currentNode, destinationPort)` 的连续 rule-owned 目的段内工作，不使用 `ANY_PORT`，
  因而不改变 base IP 或表路由 fallback 语义。
- 自定义 path finder 不使用直接 DAG 编译，因此冷缓存时仍可能生成完整基准表。
- 1024-NPU 当前单次冷编译为 35.39 s，之前同机单次结果为 27.66 s。两次测量都已避免
  9.4M 项全表，但样本不足以判断时间变化；后续仍应优化并重复测量图遍历阶段。
