# 单故障损失要求的可行性分析（M1）与降 lane 档位（M2）

本文是 v5.3 之后"故障损失要求"的可行性判断入口。所用记号如下：

- **N_phys**：设备的物理平面数。NPU 为 8，CPU 为 4，NIC / SSD 为 2。
- **N_shared**：设备与"承载该方向流量的对端"共有的平面数，取各对端中的最大值。
- **N_used**：实际承载流量的平面数。

这三个量分开记录，不混用。原要求是"损失 < 1/N（N 为平面或 lane 数）"；本文先按 N_phys 判断，再并列给出 N_shared 的结果。

## 0. 第七轮核验后的结论（取代下文中与之冲突的表述）

**模型合法性**：
- `flexspray_jointfeas.py` 的约束包括：端口出 / 入方向和 L1 汇聚容量，数据包头与逐包 ACK 开销，每条流只能走两端共有的平面，故障前后两个阶段的容量。
- 未受影响的流**完全移出**模型（不占容量），这是纯放松。
- 在相邻断点之间，分段常数速率对流体调度没有损失。
- 除共有平面限制外，没有固定流分配，也没有共同结束时刻。
- 唯一可能比实际更严的是**故障规则**：
  - **硬断链**（DOWN / DOWN_NODE）：容量在 t_f 归零是精确的，实际系统还会丢失在途数据，所以模型更宽松，**不可行即物理不可行**；
  - **优雅隔离**（ISOLATE / ISOLATE_NODE）：仿真只停止"新接纳"，端口保持原速率，已接纳和排队的数据继续排空，远端在 2 µs 通知前仍可接纳。容量立即归零的模型**比仿真更严**，所以它的不可行**不能**证明实际系统不可行。

**按故障语义重新分类**（未见种子 7，N = N_phys，健康参照 = 同种子 F0 实测，`<work>/exp/round7/jointfeas`、`round5/jointfeas`）：

| 结构（行数） | 代表 case | 模型 | ε* | 结论 |
|---|---|---|---|---|
| NPU 端口硬断，h2d（4 行） | h2d H1far s7 | 精确（容量归零） | −0.053 | **A：物理不可行**（"≤"也不可行） |
| L1 平面 0 硬断（18 行） | h2d / mixed / mixedread H4 s7 | 精确 | −0.053 / −0.053 / −0.053 | **A** |
| L1 平面 4 硬断，SSD0 失去 1 个平面（6 行） | mixed / mixedread H4p4 s7 | 精确 | −0.265 / −0.265 | **A** |
| NPU 端口优雅隔离，h2d（4 行） | h2d F1far s7 | 容量归零（更严） | −0.053 | 不能作为物理证明 |
| 同上 | 同上 | 计入本次实测排空（193 KB） | −0.053 | 用本次排空量不可行 |
| 同上 | 同上 | 搜索每个被隔离资源需要的最小排空量 D* | "≤"需要 D* = 1.83 MB，"<"需要 1.84 MB | **B**（见下） |
| L1 平面 0 优雅隔离（18 行） | mixed F4 s7 | 计入实测排空（各被隔离资源合计 4.7 MB） | −0.053 | B（未求 D*） |
| L1 平面 4 优雅隔离（6 行） | mixed / mixedread F4p4 s7 | 计入实测排空（4.9 / 32.6 MB） | −0.256 / −0.264 | B（未求 D*） |

**为什么优雅隔离归入 B**（h2d F1far 可人工核对）：
- 要满足"≤ 1/8"，隔离后必须还有至少 1.83 MB 经过被隔离的端口排空。
- 这些数据只能是故障时已接纳到该平面 TP、或已在途的数据。NPU6 在平面 3 上的发送只属于一个 TP（d2h 到一台 CPU），协议的承诺上限是每 TP 2 段 × 16 KB 再加 CC 窗口，远小于 1.83 MB。
- 所以按当前协议的承诺限制不可行（B）。如果允许任意深的预先承诺（例如把 1.8 MB 预先排进端口队列），流体上可行，所以**不是**物理证明。

**证明覆盖范围**：
- 求解过的只有种子 7 的代表 case。种子 8 的 28 行，以及同结构的其余 case，标为 **D：未求解，按结构推断**。依据是大流量需求与种子无关（只有控制小流随种子变化），健康 T_H 的差别小于 1%。
- 单设备 ε（每台设备单独受约束）与联合 ε* 分别报告。联合最优解中最差设备的损失，**不等于**每台设备各自的最小损失。

**口径**：
- 原要求按 N_phys 判断，在 A 类结构上不可达，在 B 类结构上受协议承诺限制不可达。
- N_shared（与对端共有平面数的最大值）**不是**正确的界：H4p4 在 N_shared = 4 下仍然 ε* = −0.14，实测损失 0.408 > 0.25。
- "按受损设备中最小的 N"对 h2d F1far / H1far **也不满足**：唯一受损设备是 NPU6，N = 8，损失 0.187 > 0.125。
- 对端混合的设备只有容量感知的界才一致，作为并列解释，不替换原要求。

## 1. 56 行的审计（v5.3，未见种子 7、8，`flexspray_lossreport.py`）

- 损失 ≥ 1/N_phys 的 56 行，**全部**是服务器 0 的 **NPU6 / NPU7**（N_phys = 8）。
- 这两台 NPU 承载的是 IO 类业务：
  - 与 CPU（4 个平面，与 NPU 共有平面 0–3）之间的 h2d / rh2d / d2h；
  - 与 SSD（共有平面 4–5）之间的 kv_read / kv_write；
  - 与 NIC（共有平面 0–1）之间的 d2nic。

  所以这些行的 N_shared 是 4 或 2，而不是 8。
- 故障类型：F1far / H1far（NPU 端口）、F4 / H4（服务器 0 的平面 0 的 L1）、F4p4 / H4p4（平面 4 的 L1，SSD0 失去一半端口）。
- 损失比 1/8 高出 5.5–28.3 pp，**没有**"恰好等于阈值"或数值误差级的行。
- 统计口径：
  - 损失 = 1 − goodput(故障) / goodput(F0)；
  - goodput = 该设备该方向的业务字节 / 最后完成时刻；
  - F0 为同方案、同种子的健康运行。
- 原始数据：`<work>/exp/round5/loss_v53.json`。

## 2. 联合可行性：最大化共同裕量 ε（`flexspray_jointfeas.py`）

**问题**：是否存在任何调度，使每个受影响的设备-方向 (d, dir) 同时满足

```
goodput_fault(d, dir) ≥ (1 − 1/N_d + ε) · goodput_healthy(d, dir)
```

**等价写法**：(d, dir) 的全部流在 D = T_H / (1 − 1/N + ε) 之前送达。

**模型**（与 makespan LP 一致）：
- 端口出 / 入方向容量，计入数据包头和反向 ACK；L1 上 / 下行汇聚容量；
- 每条流只能使用两端共有的平面；
- t_f 之前为健康容量，之后为故障容量。优雅隔离也按 t_f 处理，比方案实际享有的 2 µs 排空更严。

**放宽**：未受影响设备的流**不设截止时间**（要求没有约束它们）。在这种最宽松的条件下若仍不可行，则任何调度器都不可行。

**健康参照**：
- `measured`：同方案、同种子 F0 下该设备的完成时间（就是要求本身的参照）；
- `ideal`：该设备单独受约束时，健康网络下的最短完成时间（更严）。

**求解**：ε 二分到 1e-4。用 max-scale LP 的正对偶变量，给出绑定的资源（容量割）。

**结果**（种子 7，`<work>/exp/round5/jointfeas/*.json`）：

| case | 受约束的设备-方向 | N | 参照 | ε*（联合） | 单设备 ε | 严格 < 1/N | ≤ 1/N |
|---|---|---|---|---|---|---|---|
| a2a F1far | NPU12 tx/rx | 8 (phys) | measured | **+0.064** | +0.082 / +0.081 | 可行 | 可行 |
| d2d H1near | NPU0 tx/rx | 8 (phys) | measured | **+0.048** | +0.064 / +0.065 | 可行 | 可行 |
| h2d F1far | NPU6 tx/rx | 8 (phys) | measured | **−0.053** | −0.039 / −0.037 | **不可行** | **不可行** |
| h2d F1far | NPU6 tx/rx | 8 (phys) | ideal | **−0.076** | −0.061 / −0.061 | 不可行 | 不可行 |
| h2d F1far | NPU6 tx/rx | 4 (shared) | measured | +0.072 | +0.087 / +0.088 | 可行 | 可行 |

**H4p4 的含义**：
- NPU6 rx 主要是来自 SSD0 的 KV 读。SSD0 失去 2 个平面中的 1 个，这部分流量的可达容量减半。
- 因此即使改用 N_shared（取对端中的最大值，这里由 CPU 决定为 4），要求仍不可行。
- 对于对端混合的设备，任何单一的 N 都不是正确的界。一致的可达界是**容量感知**的：按该设备各对端流量加权后，被移除的可达容量比例。这正是 LP 最优解所体现的。所以我们并列报告"相对 LP 最优的额外损失"，而不替换原指标。

**结论（已被 §0 修正）**：下面这段只对硬断链成立；优雅隔离属于 B 类。原文：**结论 A（物理不可行）**：56 行所在的设备在 N = N_phys 下，即使只要求"≤"也不可行。

**可人工核对的容量割**（h2d F1far，NPU6 tx）：
- NPU6 的 d2h 流只能走它与 CPU 共有的平面 0–3。
- 健康时它在 164.5 µs 内送出 251.2 Mbit，即约 1527 Gbps，已占平面 0–3 四个端口净荷上限（4 × 392.5 Gbps）的 97%。
- t_f = 50 µs 时平面 3 被隔离。可达的最早完成时刻 = 50 + (251.2 Mbit − 4 × 392.5 × 50 µs) / (3 × 392.5 Gbps) ≈ 196.7 µs。
- 于是 goodput 损失 ≥ 1 − 164.5 / 196.7 = **16.4% > 12.5%**。
- 同时还要收它的 rx 流，ACK 占用同一组出口，联合最小损失为 17.8%。实测为 18.7%。
- LP 的绑定资源（对偶为正）正是 NPU6 在平面 0–3 上的出口，故障前后两个阶段都在其中。

**按 N_shared 判断**（已被 §0 修正）：h2d F1far 和 mixed F4 在 N_shared = 4 下可行，有 5–7 pp 裕量；**H4p4 在 N_shared 下仍不可行**（ε* = −0.14，实测损失 0.408 > 0.25）。

## 3. 可避免的部分（B + C）：实测损失与 LP 最小损失之差

| case | 设备-方向 | 实测损失 | LP 最小损失（联合） | 超出 |
|---|---|---|---|---|
| a2a F1far s7 | NPU12 tx / rx | 0.083 / 0.085 | 0.061 | +2.2 / +2.5 pp |
| d2d H1near s7 | NPU0 tx / rx | 0.089 / 0.089 | 0.077 | +1.2 / +1.3 pp |
| h2d F1far s7 | NPU6 tx / rx | 0.187 / 0.183 | 0.178 | +0.8 / +0.5 pp |

- 这些超出来自恢复限制（B：故障时已排队的数据、已承诺的读响应、segment 粒度）和在线调度（C）之和。流体 LP 没有建模包级约束，所以"超出"是上界，不能全部算作调度损失。
- 这些 case 都已满足 1/N_phys，超出量只是"可改进的空间"，不是失败。

|---|---|---|---|
| d2d / d2dread | ≥ 0.984 | ≥ 0.984 | ≥ 0.980 |
| a2a（近 / 远） | 0.968 / 0.972 | 0.953 / **0.911** | **0.609 / 0.725** |
| a2aread | 0.966 / 0.968 | **0.757 / 0.763** | **0.189 / 0.250** |

| mixedread | 0.973 / 0.977 | 0.921 / 0.955 | **0.343 / 0.355** |

- **只有 3/4 被主矩阵充分覆盖**。1/2 和 1/4 是端口真实存在的 lane 组合（x4 → x2、x4 → x1），在集合通信和热点混跑中**明显不达标**。这是未解决问题，不是压力测试。
- 1/8、1/16、1/64 不对应 4-lane 端口的 lane 组合，只作为连续限速压力测试（v5.2 轮的数据）。
- **"丢 k 条 lane"与原要求"丢 1 条 lane"的关系**：丢 k 条 lane 移除的是该端口 k/4、设备 k/32 的容量；原要求只针对单 lane（1/32）。两者分开报告，不把原要求换成 k/N。

### 4.1 因果定位（a2aread，近端 1/4，种子 1；`exp/round6/diag`、`diag2`）

1. **故障前已存在深的承诺**：t = 40 µs（故障发生在 50 µs）时，降速 NPU 平面 3 上：
   - 它作为请求方在外的 READ 约 4.1 MB；
   - 它作为响应方已接纳、未发出的响应约 3.6 MB。

   来源是健康状态下"每 TP 192 KB 读配额 × 每平面约 23 个对端"。
2. **故障后不再有新的承诺**：平面 3 的接纳字节在 40 µs 之后保持 11 MB 不变，说明分发器已经避开了平面 3。
3. **已承诺的工作无法改道**：READ 响应必须走请求所在 TP 的平面。降速端口前的 L1 下行队列一度达到 5.7 MB，按 1/4 速率要排空约 330–470 µs，于是 makespan 达到 908 µs。
4. **写方向**（a2a，近端 1/4，种子 1；`exp/round6/diag`）：降速 NPU 自己的数据在约 170 µs 就已发完（之后各平面的发送都是 0），但它的发送流和接收流直到 174–282 µs 才完成，其余流在 161–166 µs 完成。尾段来自"完成"而不是"发送"：
   - 其他写方在它慢的平面 3 下行口上，最多积压约 830 KB 已承诺的数据。SprayCC 的边沿打标没有把这部分控制在目标时延以内，原因未查明。
   - 它自己的写的 TAACK 经由同一个慢入口返回，排在这些积压之后。
   - 结构与读方向相同：慢入口上的承诺超过了它的服务速率，响应又被绑定在慢平面上。

### 4.2 本轮否定的修补

| 修补 | 结果（种子 1） | 判断 |
|---|---|---|
| 时延目标读配额（`ReadQuotaDelayTarget`，8 / 16 µs；默认关闭，代码保留） | a2aread 1/4：0.19 → 0.28–0.29；**健康 mixedread 0.974 → 0.64 / 0.81** | 否定：它只限制新的承诺，无法撤回故障前已有的；热点 SSD 的读本来 RTT 就长，被误当成慢路径 |

正确性：晚绑定开启时，6 个读恢复用例（read_far / read_near / near_stale_read / bidir / overlap_concurrent / l1_node）的 P1–P6 全部通过（`exp/round6/recov_lb`）。

**修正后的假说**（尚未实现）：
- 1/2 和 1/4 lane 下读性能差，主要原因是**已接纳进慢 TP、已分配 PSN 但尚未发出的段**，以及交换机队列中的数据。
- 只控制新的承诺（配额）或新的响应（晚绑定），都只能改善一部分。
- 根本的修复需要"未发出段的迁移"：取消慢 TP 上尚未发出的后缀段（已有 `TryCancelUnsentWqeSegment` 能力）后，重新在其他平面接纳。这些段从未进入网络，所以不涉及重复执行和 fence；但需要同步更新事务记录、lease 和请求方的记账。
- 交换机中已排队的部分不可撤回（B 类）。
- 另外，这些 case 的 eff_fixed 只有 0.19–0.76（相对 LP 最优），所以绝大部分损失是**可避免的**（B / C 类），不是物理下限。

**晚绑定的协议扩展**（已实现，默认关闭）：
- 被改绑的响应携带 4 B 的"发起请求的 TPN"（`UbRespOriginTag`）。
- 请求方把这部分字节计入发起 TP 的读配额，并以发起 TP 的身份完成该段。
- 事务层按事务身份匹配响应，与旧版逐位一致。

## 5. 第七轮：承诺状态分解、聚合授信与队头阻塞（M2–M4，种子 1，`<work>/exp/round7`）

### 5.1 状态分解（`flexspray_segstate.py`；a2aread 近端 1/4，故障在 50 µs）

**方法**：
- 以每个 READ 段为一个业务单元，键为（请求方, jetty, TaSsn）。
- 按事件时间划分状态，同一时刻每个单元只计入一个状态，所以各状态的字节数可以相加而不重复：
  - S0：请求已接纳、未发完；
  - S1：请求已发出、响应未生成；
  - S2：响应已生成、未接纳到 TP；
  - S3：响应已接纳到 TP、未发出任何字节；
  - S4：响应部分发出；
  - S5：响应已全部发出、请求方尚未完成。
- 事件由新的追踪 `SegState.csv` 提供，只在恢复追踪开启时记录。

**结果**：

| 单元集合 | 故障时刻：未进入网络（S0–S3） | 已进入网络（S4/S5） | 最后完成单元的主要等待 |
|---|---|---|---|
| (a) 降速节点作为请求方，响应走平面 3（降速节点的入口） | 3536 KB（几乎全部是 S3：在各响应方 TP 中等待） | 496 KB | 在响应方的 S3 停留约 120 µs，在交换机中的 S5 停留约 460 µs |
| (b) 降速节点作为响应方，平面 3（降速节点的出口） | 3408 KB（S3） | 496 KB | 请求的 S1 达约 420 µs，见 5.3 |

- (a) 与 (b) 是不同的业务，**没有重叠**。
- 先前的"4.1 MB 在外"属于 (a) 在请求方的视角；"3.6 MB 未发"属于 (b) 的 S3。
- 先前"接纳在 40 µs 停止"是 40 µs 采样间隔造成的假象：实际停止在 [40, 80] µs 之间。

**故障后新的请求放置并没有错**：
- 降速节点自己发往平面 3 的请求占 0.1%；
- 其他节点向它读、走平面 3 的请求占 2.5%；
- 两者都低于平面 3 的合理份额 3.4%。

**故障时刻对照**（a2aread 近端 1/4，种子 1，eff_fixed）：

| 故障时刻 | 0.1 µs | 10 µs | 50 µs | 100 µs | 140 µs |
|---|---|---|---|---|---|
| eff_fixed | 0.314 | 0.222 | 0.189 | 0.246 | 0.643 |

- 即使故障发生在启动之前也只有 0.31。原因是启动时分发器还没有任何速率信息，按平面均分，健康时每个节点约有 35 MB 的读承诺（23 个对端 × 8 个 TP × 192 KB，约 88 µs 的工作量）。
- 所以根源是**健康时的总承诺没有上界**，故障只是让其中 1/8 被困。
- 第六轮的"故障前承诺"说法需要修正：真正的问题是承诺总量，而不只是它形成于故障之前。

### 5.2 每端口聚合 READ 授信（`ReadPortBudgetBytes`，默认关闭）

**机制**：
- 每个（节点, 端口）上，经由该端口请求、尚未到达的 READ 字节总数不超过 B。
- 在端口内按**流**做加权的 max-min 公平：每个 TP 的权重是 1 / 所属流的平面数。
- 被拒绝的 TP 在端口额度释放时被唤醒；没有在外字节的 TP 始终可以接纳一个段，保证进展。

| 变体 | a2aread 健康 | 1/2 近端 | 1/4 近端 / 远端 | mixedread 健康 | 1/2 近端 | 1/4 近端 / 远端 |
|---|---|---|---|---|---|---|
| v5.3 | 0.965 | 0.757 | 0.189 / 0.250 | 0.974（逐设备 0.927） | **0.963** | 0.392 / 0.355 |
| B = 1 MB，先到先得 | 0.842 | 0.857 | 0.755 / 0.620 | 0.835 | 0.820 | 0.677 / 0.765 |
| B = 1 MB，按 TP 公平 | 0.839 | 0.881 | 0.806 / 0.825 | 0.616 | 0.628 | 0.633 / 0.640 |
| B = 2 MB，按流加权公平 | 0.956 | 0.898 | 0.592 / 0.597 | 0.958（逐设备 0.908） | **0.848** | 0.639 / 0.588 |
| B = 3 MB，按流加权公平 | 0.965 | 0.878 | 0.401 / 0.379 | 0.981（逐设备 **0.937**） | 0.810 | 0.393 / 0.412 |
| B = 2 MB，加权 + 响应晚绑定 | 0.952 | 0.895 | 0.606 / 0.653 | 0.957（逐设备 0.909） | 0.854 | 0.710 / 0.757 |

**判断**：
- 限制聚合承诺是第一个能大幅改善 1/2、1/4 lane 的机制（a2aread 1/4 最多从 0.19 提高到 0.81）。
- 但任何**静态**的 B 都在健康与降速之间取舍：
  - B 小：降速收益大，健康损失大；
  - B 大：健康时甚至更好（mixedread 逐设备 0.937），但降速收益消失；
  - mixedread 1/2 近端在所有预算下都**变差** 11–15 pp，原因未查明。
- 先到先得的唤醒造成严重不公平：B = 1 MB 时 a2a 流的完成时间分布在 126–190 µs，v5.3 为 160–166 µs。改成按流公平后健康 a2aread 恢复。这说明此前"按端口限制读预算"失败，部分原因是公平性实现，而不是聚合授信本身。
- 结论：**有限条件下成立，不作为默认**。需要的是随服务能力变化的预算（SIRD 一类的按发送方授信与反馈），这里没有实现。
- 时延目标读配额 40 / 60 µs：对降速没有任何效果，已否定。

### 5.3 队头阻塞：优先级 VL 被同一 TP 的 PSN 顺序抵消（`HolDelay.csv`）

- READ 请求走优先级 VL 1，READ 响应和 TAACK 是普通数据包，走 TP 自己的 VL（大流量用 7）。同一个 TP 的包按 PSN 顺序交付。
- 所以一个先到的请求，要等同一 TP 上 PSN 更早、还困在慢队列里的数据都到达后才能被处理。
- 实测（降速节点，从到达到按序交付的等待）：

| 场景 | 包类型 | 中位数 | p99 / 最大 |
|---|---|---|---|
| a2aread | READ 请求 | 2.6 µs | **418 µs** |
| a2aread | READ 响应 | 4.9 µs | 77 / 96 µs |
| a2a | TAACK | 2.4 µs | 38 / 50 µs |
| a2a | 写数据 | 2.2 µs | 38 / 59 µs |
| 其他节点（对照） | 各类 | — | < 12 µs |

- GBN 接收方会把乱序到达的包标为"丢弃"：不确认、等待按序。但包仍保留在接收缓存中，空洞补齐后被使用，所以不产生无效的业务字节。
  - 健康 a2aread 在 1 ms 内有 9024 个 READ 请求因越过同一 TP 上更早的数据而乱序到达；
  - 健康 a2a 有 45056 次乱序到达（逐包喷洒在 fabric 内造成的重排）。
- **尝试过的修复**：把乱序到达的无序 READ 请求提前交给事务层（`EarlyRequestDelivery`）。
  - **第一版**：所有用例挂起，包括健康用例。原因已查明：乱序包的处理函数返回 false 后，调用方直接返回，**跳过了 `CompleteInboundTaUnits`**。提前取出的请求从入站状态中删除了，却没有交给事务层，于是丢失。
  - **第二版**：在提前交付处直接调度完成，不再挂起。性能变化很小，方向也不一致：健康 a2aread +0.4 pp；mixedread 1/2 近端 +1.1 pp；1/4 近端 a2aread −1.7 pp，mixedread −2.9 pp。
  - **正确性**：P1–P6 预言机下，`fence_false_death_bidir` 的 **P6 失败**：最后一个任务完成时，活跃端口上仍有约 2 MB 的信用被占用；v5.3 和其他变体在该用例中都通过。
  - 结论：**撤回，代码已删除**。请求的队头阻塞是真实存在的（p99 418 µs），但它**不是** 1/4 lane 损失的主要原因。
- **含义**：这是协议结构层面的耦合（VL 优先级与按 TP 排序的交付），会影响降速和热点下控制类报文的及时性。修复需要更彻底的设计，例如请求 / 完成走独立的序号空间。本轮不做。

### 5.4 写方向（a2a 近端 1/4）

- 尾段原因：
  - 降速节点自己的数据在 170 µs 就已发完，但它的写的完成（TAACK）和发往它的写，要排在其平面 3 慢入口约 830 KB 的数据之后；
  - 5.3 的队头阻塞又把这些报文的等待延长到 38–59 µs（p99）。
- SprayCC 为什么没有把该慢入口的队列控制在目标时延以内（边沿打标的统计和返回），本轮**没有查清**（T19-W）。

### 5.5 发送时晚绑定（S2 迁移）与第七轮汇总

**发送时重绑定挂起的最小复现与修复**：
- **复现**：第六轮的发送时重绑定（`ResponseRebindAtSend`）在 a2aread / mixedread 的**所有**用例挂起，包括健康用例，种子 1。
- **原因**（读代码确认）：
  1. 响应在发送时被改绑到另一个 TP，如果该 TP 拒绝接纳，这个条目会以**原 TP 的队列键**放回等待；而唤醒来自新 TP 的容量事件，后者只唤醒新 TP 自己的队列键。
  2. 重试时段上已经带有 `RespOriginTpn`，不会重新选择，却仍带着新 TP 的身份交给原 TP，于是永远不会被唤醒。
- **修复**：只有新 TP **立即接纳**时才确认改绑；否则恢复段的身份字段，沿用原队列和原唤醒路径。
- **验证**：
  - 修复后 a2aread / mixedread 全部完成；
  - 50 个单元测试套件在开启状态下全部通过；
  - 22 个恢复用例的 P1–P6 全部通过。

**SIRD 式逐 TP 反馈**（`ReadBacklogFeedback`，§RESEARCH 5）：
- a2aread 1/4 近端 0.188 / 远端 0.244，v5.3 为 0.189 / 0.250，没有改善；
- 健康 mixedread 0.926（阈值 64 KB）和 0.851（32 KB），低于 v5.3 的 0.974；
- 结论：**无效，已否定**，代码保留为默认关闭的基线。
