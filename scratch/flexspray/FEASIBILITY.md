# 单故障损失要求的可行性分析（M1）与降 lane 档位（M2）

本文是 v5.3 之后"故障损失要求"的可行性判断入口。所用记号如下：

- **N_phys**：设备的物理平面数。NPU 为 8，CPU 为 4，NIC / SSD 为 2。
- **N_shared**：设备与"承载该方向流量的对端"共有的平面数，取各对端中的最大值。
- **N_used**：实际承载流量的平面数。

这三个量分开记录，不混用。原要求是"损失 < 1/N（N 为平面或 lane 数）"；本文先按 N_phys 判断，再并列给出 N_shared 的结果。

## 1. 56 行的审计（v5.3，未见种子 7、8，`flexspray_lossreport.py`）

- 损失 ≥ 1/N_phys 的 56 行，**全部**是服务器 0 的 **NPU6 / NPU7**（N_phys = 8）。
- 这两台 NPU 承载的是 IO 类业务：
  - 与 CPU（4 个平面，与 NPU 共有平面 0–3）之间的 h2d / rh2d / d2h；
  - 与 SSD（共有平面 4–5）之间的 kv_read / kv_write；
  - 与 NIC（共有平面 0–1）之间的 d2nic。

  所以这些行的 N_shared 是 4 或 2，而不是 8。
- 故障类型：F1far / H1far（NPU 端口）、F4 / H4（服务器 0 的平面 0 的 L1）、F4p4 / H4p4（平面 4 的 L1，SSD0 失去一半端口）。
- 损失比 1/8 高出 5.5–28.3 pp，**没有**"恰好等于阈值"或数值误差级的行。
- 统计口径：
  - 损失 = 1 − goodput(故障) / goodput(F0)；
  - goodput = 该设备该方向的业务字节 / 最后完成时刻；
  - F0 为同方案、同种子的健康运行。
- 原始数据：`<work>/exp/round5/loss_v53.json`。

## 2. 联合可行性：最大化共同裕量 ε（`flexspray_jointfeas.py`）

**问题**：是否存在任何调度，使每个受影响的设备-方向 (d, dir) 同时满足

```
goodput_fault(d, dir) ≥ (1 − 1/N_d + ε) · goodput_healthy(d, dir)
```

**等价写法**：(d, dir) 的全部流在 D = T_H / (1 − 1/N + ε) 之前送达。

**模型**（与 makespan LP 一致）：
- 端口出 / 入方向容量，计入数据包头和反向 ACK；L1 上 / 下行汇聚容量；
- 每条流只能使用两端共有的平面；
- t_f 之前为健康容量，之后为故障容量。优雅隔离也按 t_f 处理，比方案实际享有的 2 µs 排空更严。

**放宽**：未受影响设备的流**不设截止时间**（要求没有约束它们）。在这种最宽松的条件下若仍不可行，则任何调度器都不可行。

**健康参照**：
- `measured`：同方案、同种子 F0 下该设备的完成时间（就是要求本身的参照）；
- `ideal`：该设备单独受约束时，健康网络下的最短完成时间（更严）。

**求解**：ε 二分到 1e-4。用 max-scale LP 的正对偶变量，给出绑定的资源（容量割）。

**结果**（种子 7，`<work>/exp/round5/jointfeas/*.json`）：

| case | 受约束的设备-方向 | N | 参照 | ε*（联合） | 单设备 ε | 严格 < 1/N | ≤ 1/N |
|---|---|---|---|---|---|---|---|
| a2a F1far | NPU12 tx/rx | 8 (phys) | measured | **+0.064** | +0.082 / +0.081 | 可行 | 可行 |
| d2d H1near | NPU0 tx/rx | 8 (phys) | measured | **+0.048** | +0.064 / +0.065 | 可行 | 可行 |
| h2d F1far | NPU6 tx/rx | 8 (phys) | measured | **−0.053** | −0.039 / −0.037 | **不可行** | **不可行** |
| h2d F1far | NPU6 tx/rx | 8 (phys) | ideal | **−0.076** | −0.061 / −0.061 | 不可行 | 不可行 |
| h2d F1far | NPU6 tx/rx | 4 (shared) | measured | +0.072 | +0.087 / +0.088 | 可行 | 可行 |
| h2d F1far | NPU6 tx/rx | 4 (shared) | ideal | +0.049 | +0.064 / +0.064 | 可行 | 可行 |
| mixed F4 | 服务器 0 的 10 台设备，20 个方向 | 8 / 4 (phys) | measured | **−0.053** | NPU0–5：+0.103…+0.111；**NPU6 tx −0.039、rx −0.037；NPU7 rx −0.033**；CPU +0.087…+0.278 | **不可行** | **不可行** |

**结论 A（物理不可行）**：56 行所在的设备在 N = N_phys 下，即使只要求"≤"也不可行。

**可人工核对的容量割**（h2d F1far，NPU6 tx）：
- NPU6 的 d2h 流只能走它与 CPU 共有的平面 0–3。
- 健康时它在 164.5 µs 内送出 251.2 Mbit，即约 1527 Gbps，已占平面 0–3 四个端口净荷上限（4 × 392.5 Gbps）的 97%。
- t_f = 50 µs 时平面 3 被隔离。可达的最早完成时刻 = 50 + (251.2 Mbit − 4 × 392.5 × 50 µs) / (3 × 392.5 Gbps) ≈ 196.7 µs。
- 于是 goodput 损失 ≥ 1 − 164.5 / 196.7 = **16.4% > 12.5%**。
- 同时还要收它的 rx 流，ACK 占用同一组出口，联合最小损失为 17.8%。实测为 18.7%。
- LP 的绑定资源（对偶为正）正是 NPU6 在平面 0–3 上的出口，故障前后两个阶段都在其中。

**按 N_shared 判断**：同一设备在 N_shared = 4 下可行，有 5–7 pp 的裕量；按 N_shared 计，实测损失全部 < 1/N_shared。**这只是另一种解释，并不替代逐设备的结果**；原要求中的 N 应如何取，需出题方确认（DELIVERY §6）。

## 3. 可避免的部分（B + C）：实测损失与 LP 最小损失之差

| case | 设备-方向 | 实测损失 | LP 最小损失（联合） | 超出 |
|---|---|---|---|---|
| a2a F1far s7 | NPU12 tx / rx | 0.083 / 0.085 | 0.061 | +2.2 / +2.5 pp |
| d2d H1near s7 | NPU0 tx / rx | 0.089 / 0.089 | 0.077 | +1.2 / +1.3 pp |
| h2d F1far s7 | NPU6 tx / rx | 0.187 / 0.183 | 0.178 | +0.8 / +0.5 pp |

- 这些超出来自恢复限制（B：故障时已排队的数据、已承诺的读响应、segment 粒度）和在线调度（C）之和。流体 LP 没有建模包级约束，所以"超出"是上界，不能全部算作调度损失。
- 这些 case 都已满足 1/N_phys，超出量只是"可改进的空间"，不是失败。

## 4. 实际降 lane 档位（M2，4-lane 端口，v5.3，种子 1、2，`<work>/exp/round6/lanes`）

数值为两个种子中最差的 eff_fixed：

| 场景 | 3/4（丢 1 条 lane） | 1/2（丢 2 条） | 1/4（丢 3 条） |
|---|---|---|---|
| d2d / d2dread | ≥ 0.984 | ≥ 0.984 | ≥ 0.980 |
| a2a（近 / 远） | 0.968 / 0.972 | 0.953 / **0.911** | **0.609 / 0.725** |
| a2aread | 0.966 / 0.968 | **0.757 / 0.763** | **0.189 / 0.250** |
| mixed | 0.936 / 0.935 | 0.935 / 0.933 | **0.661 / 0.648** |
| mixedread | 0.973 / 0.977 | 0.921 / 0.955 | **0.343 / 0.355** |

- **只有 3/4 被主矩阵充分覆盖**。1/2 和 1/4 是端口真实存在的 lane 组合（x4 → x2、x4 → x1），在集合通信和热点混跑中**明显不达标**。这是未解决问题，不是压力测试。
- 1/8、1/16、1/64 不对应 4-lane 端口的 lane 组合，只作为连续限速压力测试（v5.2 轮的数据）。
- **"丢 k 条 lane"与原要求"丢 1 条 lane"的关系**：丢 k 条 lane 移除的是该端口 k/4、设备 k/32 的容量；原要求只针对单 lane（1/32）。两者分开报告，不把原要求换成 k/N。

### 4.1 因果定位（a2aread，近端 1/4，种子 1；`exp/round6/diag`、`diag2`）

1. **故障前已存在深的承诺**：t = 40 µs（故障发生在 50 µs）时，降速 NPU 平面 3 上：
   - 它作为请求方在外的 READ 约 4.1 MB；
   - 它作为响应方已接纳、未发出的响应约 3.6 MB。

   来源是健康状态下"每 TP 192 KB 读配额 × 每平面约 23 个对端"。
2. **故障后不再有新的承诺**：平面 3 的接纳字节在 40 µs 之后保持 11 MB 不变，说明分发器已经避开了平面 3。
3. **已承诺的工作无法改道**：READ 响应必须走请求所在 TP 的平面。降速端口前的 L1 下行队列一度达到 5.7 MB，按 1/4 速率要排空约 330–470 µs，于是 makespan 达到 908 µs。
4. **写方向**（a2a，近端 1/4）：降速 NPU 平面 3 的发送端未发送约 100–360 KB；对端发往它的 L1 下行队列最多约 830 KB。幅度比读小，但 eff 仍只有 0.609。原因尚未完全定位。

### 4.2 本轮否定的修补

| 修补 | 结果（种子 1） | 判断 |
|---|---|---|
| 时延目标读配额（`ReadQuotaDelayTarget`，8 / 16 µs；默认关闭，代码保留） | a2aread 1/4：0.19 → 0.28–0.29；**健康 mixedread 0.974 → 0.64 / 0.81** | 否定：它只限制新的承诺，无法撤回故障前已有的；热点 SSD 的读本来 RTT 就长，被误当成慢路径 |
| 统一缩小读配额（64 KB；以及 64 KB 加 4 段读管线） | a2aread 1/4：0.54–0.58；1/2：0.88–0.91；健康 a2aread −1.3 pp；**健康 mixedread 0.974 → 0.67** | 否定：任何静态配额都无法同时满足热点 SSD（需要深承诺）和降速平面（深承诺会被困住） |

| READ 响应晚绑定，生成时无条件改绑（`ResponseLateBinding`，默认关闭） | **健康 a2aread 0.965 → 0.692**、mixedread 0.974 → 0.717 | 否定：覆盖了请求方自己的平面选择（包括 v5.3 的入口打标调度），响应向估计最快的 TP 扎堆 |
| 同上，加滞回：只有当请求所在 TP 的排空时间超过最佳 TP 的 K 倍时才改绑（K = 4，`ResponseRebindRatio`） | 健康不变（0.965 / 0.972–0.973）；种子 1、2：a2aread 1/4 近端 0.189 → 0.274，远端 0.250 → 0.249；1/2 约 ±2 pp；mixedread 1/4 近端 +7 / +9 pp（0.392 → 0.461、0.343 → 0.433），远端 +9 / +11 pp（0.355 → 0.440、0.421 → 0.528）；K = 2 时健康 mixedread 降 11 pp | **部分有效，不作为默认**：1/4 lane 时排空时间比只有约 4，正处在阈值上；而且大部分响应在故障前就已接纳进慢 TP（每 TP 约 8 段，带 PSN），生成时的改绑已来不及 |
| 发送时改绑（移动尚未接纳的响应） | 实现后**所有** case 挂起（包括健康） | 实现问题：在 TP 队列之间移动条目，破坏了 RTP 发送队列的调度不变量。已撤回，未能评估 |

正确性：晚绑定开启时，6 个读恢复用例（read_far / read_near / near_stale_read / bidir / overlap_concurrent / l1_node）的 P1–P6 全部通过（`exp/round6/recov_lb`）。

**修正后的假说**（尚未实现）：
- 1/2 和 1/4 lane 下读性能差，主要原因是**已接纳进慢 TP、已分配 PSN 但尚未发出的段**，以及交换机队列中的数据。
- 只控制新的承诺（配额）或新的响应（晚绑定），都只能改善一部分。
- 根本的修复需要"未发出段的迁移"：取消慢 TP 上尚未发出的后缀段（已有 `TryCancelUnsentWqeSegment` 能力）后，重新在其他平面接纳。这些段从未进入网络，所以不涉及重复执行和 fence；但需要同步更新事务记录、lease 和请求方的记账。
- 交换机中已排队的部分不可撤回（B 类）。
- 另外，这些 case 的 eff_fixed 只有 0.19–0.76（相对 LP 最优），所以绝大部分损失是**可避免的**（B / C 类），不是物理下限。

**晚绑定的协议扩展**（已实现，默认关闭）：
- 被改绑的响应携带 4 B 的"发起请求的 TPN"（`UbRespOriginTag`）。
- 请求方把这部分字节计入发起 TP 的读配额，并以发起 TP 的身份完成该段。
- 事务层按事务身份匹配响应，与旧版逐位一致。
