**关于 1/N**：这里只给出带定义的结论，不笼统宣称"严格小于 1/N"。

- 定义：损失 = 1 − makespan(F0) / makespan(故障)，即相对健康的吞吐损失；N = 受损设备中平面数最少者的平面数。
  - NPU：N = 8；
  - CPU：N = 4（h2d、mixed 中的 F4/H4）；
  - SSD/NIC：N = 2。
- 在这个定义下，未见种子上所有 v5.2 case 都满足损失 ≤ 1/N：
  - NPU 故障 ≤ 10.5%（d2d 0.090、a2a 0.105）；
  - 涉及 CPU 的 15.8–18.9%；
  - SSD 平面 ≤ 40.5%。
- 如果 N 改为"8 个平面"，h2d、mixed F4/H4 和 SSD/NIC 平面故障都不满足。
- 完成率、故障后的 LP 效率（`eff_fixed`）和相对健康的损失，三者分别报告；`eff_fixed` > 1 不代表超过最优。

### 0.3 恢复语义声明

| 性质 | 结论 | 标签 |
|---|---|---|
| 完成恰好一次 | 每个 (发起方, jetty, WQE, TaSsn) 只完成一次，每个任务只完成一次 | 已实现并验证（oracle P1，14 个用例 + 回归） |
| 已完成即已执行 | 每个完成的段，都在目标端以相同的 opcode、地址和长度执行过 | 已实现并验证（P2） |
| 覆盖完整 | 完成的段恰好覆盖 [0, 任务字节数) | 已实现并验证（P3） |
| **远端执行恰好一次** | **不成立**：重发会使目标端重复执行 3–12 个段（每个用例 48–196 KB）。WRITE/READ 在内容相同的前提下是幂等的 | 已实现并验证（是"否定"的结论） |
| 有依赖顺序的重叠写，最后写者正确 | 成立，前提是 replay fence 开启 | 已实现并验证（P4） |
| 发起方完成后，不再有旧副本在目标端执行 | fence 开启时成立：near_stale_slow 中 10 → 0。fence 关闭时可以复现违例，作为负对照 | 已实现并验证（P5） |
| 活端口的 credit 守恒 | 仿真结束时活端口上没有滞留的 credit；断口两端的滞留不计 | 已实现并验证（P6） |
| 原子操作 | 不重发：目标端没有按 TaSsn 去重 | 范围之外（T1） |
| 同组所有平面都失效 | WQE 被拒绝，而不是报错完成 | 范围之外（T1） |
| 内容级（数据值）正确性 | 仿真器不保存内存内容，无法检验 | 未解决 |

oracle 的作用范围：
- 能证明：事件层面的事实（每个目标端执行、每个发起方完成）；
- 不能证明：数据内容，以及比段更细的顺序。
- 偏移的计算：模型把一个 WQE 所有段的地址都设为 WQE 基址，所以偏移按 TaSsn 顺序推出。

**replay fence**：
- 重发的段携带死 TP 的 TPN，这是一个 4 B 的请求头扩展，仿真中用 tag 表示，不增加包长。
- 目标端收到后，封住与该 TPN 配对的 TP，丢弃它后续收到的数据包。

### 0.4 第四轮的正确性审计与修复

1. **旧路径滞留副本的晚执行**【已实现并验证】
   - 场景：B 的平面 3 在 t=0 降到 1/4，随后 A 的平面 3 端口硬断；同时有 3 个依赖链 WRITE，以及向 B 的背景 incast。
   - 结果：旧路径的慢队列里还留着副本，它们在发起方完成之后才被执行（10 次），可能覆盖较新的数据。replay fence 修复后为 0。
   - 回归：`flexspray_regress.py` 中的 `fence_on` / `fence_off`。
2. **4 KB 尾段挂起的定位**【已实现并验证】
   - 现象：一个 a2a WRITE 永远不完成。目标端 TP 上有一个 TAACK 在等待，而该 TP 的 2 段发送管线被另一个 WQE 的两个未发段占满。随后这两个段被 `FinishWqe` 取消，但没有任何事件唤醒那个 TAACK。
   - 取消的原因：`PushWqe` 按 ceil(size/16 KB) 预留 TaSsn，而尾段切出了更多的小段，于是 WQE 在最后几段发出之前就被判为完成。
   - 修复：预留数等于实际切段数；取消未发段后唤醒等待该 TP 容量的工作。这个唤醒缺失原本就存在，只是一直没有被触发。
   - 回归：单元测试 + `tail4k`。
   - 修好后重测尾段小段本身：读混跑最差设备从 0.889 降到 0.874，**作为优化被否定**。
3. **死 TP 不再触发重传定时器**；SprayCC 与 CAQM 在多次超时、部分 ACK 加超时再加迟到 ACK、重复 ACK 这几种情况下都没有下溢或重复释放（单元测试）。【已实现并验证】
4. **交错的 WQE 可能被提前判为完成**【仍是假说，T14】
   - 一个 jetty 中多个 WQE 的段会交错占用 TaSsn，`IsWqeCompleted` 只判断预留区间的末尾。
   - FlexSpray 的全部实验中 P3 都通过，所以目前没有观测到实际影响。

### 0.5 mixed F1ssd / H4p4：因果分解与修复

**因果链**（种子 1，F1ssd：SSD0 丢掉平面 4 的端口）：
1. SSD0 的唯一剩余端口由 6 条等长的 KV incast 写共享，分配不公平：NPU28 那条到 250 µs 时只完成 1.88 MB，其他各条为 2.18–2.62 MB。
2. 260 µs 时其余各条已完成，只剩它一条；它的窗口被 incast 压小，每 2 µs 只回升 5% 线速，回到 400G 约需 33 µs。
3. 因此 SSD0 收方向在 270–300 µs 只有 0.28–0.46，makespan 被拉长 30 µs。
4. H4p4 的机制相同。

**修复**：`AiFraction` 0.05 → 0.15，属于参数改动，没有新机制。

| | v5.1 | v5.2 |
|---|---|---|
| mixed F1ssd，种子 1 / 2 / 5 / 6 | 0.899 / 0.946 / 0.975 / 0.964 | 0.961 / 0.961 / 0.975 / **0.919** |
| mixed H4p4，种子 1 / 2 / 5 / 6 | 0.870 / 0.949 / 0.948 / 0.948 | 0.950 / 0.950 / 0.945 / 0.943 |

- 结论：4 个种子都 ≥ 0.90，**但并非每个种子都比 v5.1 好**。种子 6 的 F1ssd 比 v5.1 低 4.5 pp，原因仍是 incast 流之间的不公平：完成时间分布在 226–298 µs，加性增量的改变只是换了最后剩下的那条流。
- 标签：**有限条件下成立**。根因中的"incast 不公平"仍是**未解决**。
- 没有回退到优雅排空，也没有使用理想通知。

### 0.6 读混跑最差设备 0.889：关键路径分解（未解决，T11）

- **稳态没有损失**：[10, 146] µs 内，最差设备（a2a 响应方 NPU 的 tx）利用率为 1.000，所以 0.889 全部来自尾段。
- **关键路径**：
  1. SSD0 的需求为 1.003，它决定 makespan，并且只有平面 4/5。
  2. 热点读者在平面 4/5 的入口上同时收 KV 响应和 a2a 响应，L1 下行口形成 400–780 KB 的常驻队列；读者的其他 6 个平面没有这样的队列。
  3. 156 µs 以后，读者只剩平面 4/5 在排空（收方向 0.25–0.35），SSD0 的发方向为 0.34–0.83。读者每个 KV TP 上一直有约 180 KB 的请求在外，而 SSD0 端的响应积压为 0，说明这些响应卡在读者侧的入口队列里。
  4. 结果：发往热点读者的 a2a 流在 165–173 µs 才完成，其他流在 154–158 µs 完成，于是这些流的响应方（最差设备）被拖到 173 µs。
- **本轮否定的机制**（代码已撤回）：
  - 读请求按本端端口的全部未回读字节打分：0.889 / 0.884（每个 TP 的配额都已占满，分发器几乎没有选择余地）；
  - 按读完成延迟的 EWMA 打分：mixedread 0.69 / 0.75，d2dread 0.988 → 0.913（请求扎堆到一个平面后在等待中空转）；
  - 4 KB 尾段：0.874。
  - 加上前几轮否定的方法，共 7 种。
- **浅缓冲下的拥塞代价**：
  - mixedread 效率 0.938/0.946 → 0.924/0.925；
  - 交换机队列峰值约 805 KB；
  - 交换机端口平均有 1.5% 的时间处于 credit 阻塞，最严重的端口为 40%，主机端口为 0.4%；
  - 写混跑没有阻塞。
- 其他门限没有因读混跑的尝试受影响，相关代码已全部撤回。

### 0.7 探测、重传与 CC 的交互（`flexspray_fdreport.py`）

- **新增协议扩展**：TP opcode 0x4（PROBE）和 0x7（PROBE_REPLY），只携带 TP 头，走控制 VL；replay fence 的 4 B 请求头扩展。
- **未见种子上的硬断链**（v5.2，64 个 case）：
  - 怀疑 4277 次，其中 1827 次被解除；
  - 本地判死 3284 个，远端判死 2450 个，**误判 0**；
  - 发出探测 9177 个；应答 939 个解除怀疑、886 个为重复应答、**迟到 0**；无应答的 7352 个全部发生在已断的路径上。
- **检测时间**：
  - 从首次使用算起为 25.0–31.7 µs，即 10 µs 沉默 + 3 × 5 µs 探测；
  - 从故障算起为 23.6–123 µs。上限来自"惰性检测"：故障时空闲的 TP，要等下一次被使用时才开始检测，在此之前它不承载流量。
- **RTO（CC 开启）**：
  - 硬断链中 1409 次，其中 1394 次发生在断路或故障平面的 TP 上，1318 次发生在 TP 处于"怀疑"状态时；**伪 RTO 15 次**。
  - 优雅故障（268 个 case，没有任何丢包）：怀疑 9846 次全部解除，判死 0，伪 RTO 40 次（单个 case 最多 6 次），原因是排队时间超过了 RTO。
- **反例**（两台服务器，B 的平面 3 降速，同时有 incast，没有丢包）：

| 降速 | 怀疑 | 判死 | 伪 RTO | 最后一个任务完成 |
|---|---|---|---|---|
| 1/4 | 16 | 0 | 0 | 167 µs |
| 1/8 | 108 | 0 | 2 | 354 µs |
| 1/16 | 410 | 0 | 74 | 1.40 ms |
| 1/64 | 1119 | **4（误判）** | 约 50 | 3 ms 时仍未完成 |

  - 1/64 时，探测往返要经过两跳 1/64 的链路，超过了 3 × 5 µs（T15）。
  - 深度降速时尾段很长：降速发生时，incast 启动阶段已在慢口堆了约 1.8 MB，发送端无法改道（T13，**未解决**）。
  - 主矩阵只覆盖 3/4（x4 → x3）的降 lane。

### 0.8 对照方案

### 0.3 T10 的根因与修复（上行收敛 fabric，mixed F2up）

原假说"约 1 MB 的 CBFC 反压太晚"经观测**被推翻**。新增的逐 TP 采样器（`TpSample.csv`）和分发等待计时（`DeferSample.csv`）显示：

1. 拖尾的是另一条流：服务器 3 的 CPU1 → 服务器 0 的 NPU7。被隔离的链路是双向的，进入服务器 0 平面 3 的下行容量少了 1/8。
2. 这条流在平面 3 上只分到 4.2 MB，其他平面各 7.4 MB。平面 3 的 TP 在途只有 7–12 个包（其他平面 20–26），排空时间估计与其他平面相同。fabric 中只有 L2→L1 的一条剩余链路排了 82 KB 的队。
3. 机制：平面 3 短暂变慢 → 投递速率估计下降 → 严格等待的分发器少给该平面 → TP 没有积压可发，变成"应用受限" → 应用受限期间测得的仍是低速率 → 估计值一直回不去。因分发等待而空等的时间从 97 µs 增加到 157 µs。v4 的严格等待放大了这个循环（0.891 → 0.874）。

修复（`DeliveryRateAppLimitedGuard`，与 BBR 的做法相同）：TP 没有积压时测得的样本，只能调高估计，不能调低。
- v5 曾把这项保护用于所有 TP，导致读请求方被误判：读请求方的发送队列为空，通常是因为读配额已满，属于受网络限制。结果读混跑 F3ssd 的损失比下限高 3.2 pp。v5.1 改为只作用于没有未回读字节的 TP。

结果：osub mixed F2up 在 4 个种子中最差 **0.914**，关闭保护的消融为 0.866；其他 49 个场景没有回退。

### 0.4 读混跑尾段（0.883 → 0.889）与读拥塞控制

- **可行性**：用带截止时间的流体 LP 做了检验（`flexspray_feasibility.py`）。每台设备的截止时间 = 它的字节数 / (0.9 × 端口协议上限)，每条流继承两端截止时间中较早的那个。结论：mixed 中所有设备同时 ≥ 0.9 **可行**，上限 U* = 0.944；mixedread 在 U = 0.9 时同样**可行**。所以 0.9 不是负载本身的不可达限制。
- **差距来源**：最差设备是**响应方**，它自身的需求只有端口上限的 93%。它最后一条流的完成时间由热点读者决定，而热点读者的入口已经饱和。要达到 0.9，热点读者必须在约 168 µs 内收完，即整体效率 ≥ 0.968；当前约为 0.93–0.94。
  - 损失来自启动爬升（约 1–2 µs）和逐流尾段：每条流在每个平面上只有约 17 Gbps，一个 16 KB 段要排空 7.7 µs。
- **试过并被否定的四种机制**（代码已撤回）：
  1. 尾段改用小段：读混跑从 0.93 降到 0.87；4 KB 尾段时写混跑挂起；
  2. 按响应上的拥塞标记做 AIMD 调整读预算（即评审建议的机制）：降到 0.69–0.73；
  3. 调整 per-TP 读配额（96 / 384 KB）、读管线深度 16、8 KB 段：全部变差；
  4. 按端口限制读预算（第二轮）：降到 0.62–0.78。
- **v5.1 的结果**：0.889（4 个种子）。**未关闭**，记为 T11。
- 关于"读响应豁免 CC"：评审的判断正确，这只解决了"响应方重复门控"造成的性能问题，并不等于读拥塞控制已经完整解决。浅缓冲读混跑仍有约 41% 的端口阻塞（对照方案 37–50%），v5.1 浅缓冲读混跑效率为 0.924。
  - 请求方按标记收缩读预算会严重损失吞吐，原因是读配额的粒度（16 KB 段，每个 TP 只有十几个段）太粗，AIMD 很难稳定在合适的位置。

### 0.5 硬断链（T1）与无预言机的故障感知（T3）

**能力核查**（本分支原有机制）：

| 故障位置 | 原有机制能否恢复 | 缺口 | 本轮新增 |
|---|---|---|---|
| L1–L2 单条链路 | 能：`UbLink::Fail` + `UbReliableRerouting`，交换机保留原包，等 LastAck 后迁移，不丢包。限制：每次仿真只能坏一条链路、必须在流量开始前布防 | 多条链路同时失效 | `DOWN` 动作：两端交换机立即把断口移出路由；排队中丢失的包由 TP 的 GBN 重传恢复 |
| 端点单端口 | 不能：TP 绑定在已断的端口上，重传只在原 TP 上进行 | 判定 TP 死亡、跨 TP 重发 | 端口硬断、故障检测、段重新派发 |
| 整个 L1 / 平面 | 不能（多条链路） | 同上 | `DOWN_NODE` |

**机制**：

- **硬断**：链路两端的端口丢弃所有发送、在途和到达的包。已断端口不再等待死对端回送 credit，所以上游不会被永久阻塞。只有链路两端知道这件事，没有全局通知。
- **检测**：TP 有在途工作且对端沉默 10 µs → 进入"怀疑"（可逆，暂停接纳新段）→ 在控制 VL 上发送 PROBE → 对端回 PROBE_REPLY 即解除；连续 3 次、每次 5 µs 无应答 → 判死。
  - **新增协议字段**：TP opcode 0x4（PROBE）和 0x7（PROBE_REPLY），原为保留值，报文只有 TP 头。
  - 探测走高优先级 VL，所以数据 VL 再拥塞也能在几微秒内得到应答。
- **重新派发**：死 TP 上未完成的 WRITE/READ 段，复制后重置传输状态，转到同组中排空时间最小的存活成员。
  - transport-work lease 随之迁移，记录重新绑定到新 TP。
  - 只有记录中当前那一代 TP 的完成会被接受，旧路径迟到的响应被安静地忽略，所以保证恰好完成一次。
  - 原子操作不重发：目标端没有按 TaSsn 去重，重复执行不安全。

**结果**（FlexSpray v5.1，两个种子；对照方案开启 GBN 重传）：

| 硬故障 | FlexSpray v5.1：完成 / 效率 | 丢失 | 重新派发的段 | 远端判死时间（故障后） | spray / adaptive+CAQM / spray+DCQCN |
|---|---|---|---|---|---|
| H1near/H1far（NPU 端口）× 7 个场景 | 28/28，0.942–0.988 | 10–1440 KB | 5–511 | 23.6–29.5 µs | 除 h2d H1near 外全部挂死 |
| H4（L1 整体）× 7 个场景 | 14/14，0.947–0.987 | 0.2–8.7 MB | 23–3593 | 23.4–30.6 µs | 全部挂死 |
| H2up（L1 上行口，fabric 内）× 7 个场景 | 14/14，0.932–0.983 | 0–21 KB | 0（由重传恢复） | 不需要判死 | 完成，但 mixed 0.59–0.67、mixedread 0.60–0.79；adaptive+CAQM 在 d2d/d2dread/h2d 挂死 |
| H1ssd / H4p4（SSD 平面） | 8/8，0.870–0.987 | 0.1–7.8 MB | 37–2020 | 首次 23.8–24.0 µs，最晚 122.8 µs（含惰性检测） | 全部挂死 |

- 部分 TP 在故障发生时处于空闲，要等下一次被使用才开始检测，所以最晚的判死发生在故障后约 123 µs；在此之前它们没有承载流量。
- **消融**：
  - 关闭故障检测（`nofd`）：所有端点和 L1 硬断挂死；
  - 关闭重传（`nortx`）：H2up 挂死；
  - 健康和优雅故障场景下，两者一起关掉的差别在 ±1 pp 以内，说明这些机制平时没有代价。
- **反例（不能把仍可工作的 TP 判死）**：在以下场景中，"怀疑"最多出现 3169 次，但全部被探测应答解除，误判死亡为 0：
  - 不开 CC 的重度 incast（数据 VL 排队十几 MB）；
  - 浅缓冲 incast（端口 credit 阻塞约 80%）；
  - 降 lane；
  - 读热点混跑。
- **重传必须与 CC 一起使用**：不开 CC 的重度 incast 打开重传后，排队时延超过 25.6 µs 的重传超时，会引起多余重传，效率掉到 0.726。FlexSpray 始终开启 SprayCC，开启后 incast 为 0.995。
- **本轮发现并修复的问题**：
  - **SprayCC 的重传死锁**：SprayCC 原先没有实现"重传超时释放在途窗口"。硬断链后，窗口被已丢失的读响应占满，而 GBN 重传又受同一个窗口限制，于是读事务永久挂起（`67471995`）。
  - **对照方案 adaptive+CAQM 加重传**：在 H2up 的 d2d/d2dread/h2d 中也会挂死。CAQM 实现了窗口回退，原因未查。
- **代价分开报告**：
  - 容量下降：同一位置优雅隔离的损失；
  - 检测等待：远端约 25 µs，期间发往死路径的包全部丢失（"丢失"列）；
  - 重发开销："重新派发的段"列 × 16 KB；
  - 恢复后的稳态：见时间序列图 `fig/ts_d2d__H1far.png`、`fig/ts_a2a__H4.png`、`fig/ts_mixed__H4.png`（虚线为第一次远端判死）。
- 优雅隔离（`ISOLATE`，运维主动发起的保护切换）仍由管理面通知远端，时延可配。真正的意外故障，应当用 `DOWN` 加故障检测来建模。

## 3. 指标口径（本轮重新定义）

**效率**：效率 = T_ideal / 实测 makespan，两个种子取较差的一个。T_ideal 由流体 LP 求出：

- 流可以在共有平面上任意拆分；端口容量按线上字节计，数据为 (4096+78)/4096，ACK 为 62–70 B/包；同时约束 L1 的上行和下行汇聚容量。
- **与"优雅隔离"保持一致**：仿真中被隔离端口上的已排队和在途流量会照常排空。对每个被隔离的资源，LP 允许它在 t_f 之后承载与仿真实测相同的排空字节数。修正前，有 18 个 case 的效率大于 1；修正后没有。
- **错峰启动**：LP 按 {0, 各流释放时间, t_f} 分段求解，结果精确；对没有释放时间的 case，与原 LP 结果完全一致。

**逐设备端口利用率**（`flexspray_portutil.py`），对每个设备、每个方向分别计算：

- 分子：实测的 TP payload 速率，只统计该设备在这个方向上实际承载流量的端口。
- 分母（协议上限）：Σ 端口 (当前速率 × 时长 − 本端口上的非数据字节) / 数据开销系数。
  - 非数据字节包括反向 ACK 和 credit 帧，按实测扣除；
  - 降 lane 按降级后的速率积分；
  - 被隔离的端口在 t_f 后只计它实际排空的字节；
  - 每个平面的上限再与对端端口的可达容量取较小值，例如对端被隔离时该平面上限为 0。
- 两个时间窗口：
  - **全程**：设备自己的忙碌期 [0, 最后一条流完成]，包含启动和尾段，口径最严格；
  - **稳态**：[10 µs, 0.95 × 首条流完成]，故障场景再拆成故障后稳态 [t_f+10 µs, …] 和故障瞬态 [t_f, t_f+10 µs]。
- 另报两种口径：payload / 线速（约等于协议利用率 × 0.96）、线上利用率。
- **需求检查**：需求 = 设备字节数 / 无故障时的 T_ideal。核心场景中所有设备的需求都 ≥ 0.9 × 端口上限，没有"需求很少所以看起来效率高"的设备，因此评审担心的那种情况不存在。错峰和 incast 场景按设计不饱和，不进逐设备表。

**故障损失**：

- 计算方式：1 − 受损设备带宽 / 同一方案无故障运行时的带宽，取三个窗口：稳态 [t_f+10, end]、全程 [t_f, end]、最初 10 µs [t_f, t_f+10]。
- 对比的物理下限不再用 1/N，而是**实际被移除的容量占比**：受损设备实际承载流量的平面数中被去掉的份额，降 lane 按 1/lane 计。
  - 例如 h2d 场景中 NPU6 只用 6 个平面，下限为 1/6；F4p4 涉及多个设备，按容量加权。

**暴露量**：t_f 之后仍然经过被隔离资源的线上字节数及持续时间。它是硬断链的代理指标：换成突然断链，这些字节会丢失并需要重发。

**拥塞与开销**（采样器新增的列）：

- 交换机输出队列（VOQ + egress）的峰值和均值；
- CBFC 因缺 credit 而阻塞的时间占比；
- 控制小包 p99 时延；
- 接收端乱序距离（PSN），以及每个 TP 乱序缓存的最大包数。

## 4. FlexSpray 设计（v4）

| 层 | 机制 | 版本 |
|---|---|---|
| 交换层 | `ADAPTIVE_RATE`：逐包选 (VOQ + egress + 下游已消耗 credit) / 端口当前速率最小的出口 | v1 |
| 端侧仲裁 | `TpGroupFairShare`：主机出口在各 TP 间做 SFQ，权重为 1/k，k 为该流的平面数。**v3 改为只计未被隔离的平面**（`TpGroupFairShareUsableOnly`） | v1 / v3 |
| 端侧分发 | `MIN_DRAIN_TIME`：segment 分给"(未发 + 在途 + 未回的读响应) / 实测投递速率"最小的平面。**v4 采用严格等待**（`TpgDispatchSlack=0`）：只要最好的可用平面比最好的平面慢就等待。segment 为 16 KB | v1 / v4 |
| 读路径 | 每个 TP 的读配额为 192 KB | v1 |
| | 读请求和读响应有单独的发送管线深度，为 8（`MaxActiveReadSegments`） | v2 |
| | 读请求走控制 VL（`ReadRequestVl=1`） | v3 |
| | 流失去平面后，读配额重新分摊到剩余平面（`ReadQuotaFollowsUsablePlanes`） | v3 |
| | 读响应不受 SprayCC 窗口门控（`CcExemptReadResponses`） | v3 |
| 拥塞控制 | SprayCC：只在最后一跳打标（排队 > 2 µs）；接收端统计 marked/total；每 2 µs 一个固定周期做 DCTCP 式降速；同一 TPG 内各 TP 耦合加速；在途上限为 rate × (baseRTT + 8 µs) | v1 |

v3 各项改动的动机，均来自本轮新覆盖暴露出的根因：

- **读请求被浅管线卡住**：发送管线深度 2 × 16 KB 同时限制了读请求，导致 a2aread 只有 0.79。读的接纳本来就由读配额约束，响应走哪个平面也由请求决定，所以给读单独一个更深的管线，不会损失分发的灵活性。
- **读请求排在 incast 数据后面**：读请求虽然很小，但在 SSD0 被打满的入口上排在 incast 数据后面，拉长了每次读的往返时间。改走控制 VL 后：F3ssd 从 0.866 升到 0.935（单种子，下同）；加上配额重新分摊和按可用平面计权，F1ssd 从 0.807 升到 0.956，F4p4 从 0.807 升到 0.951。
- **SprayCC 误伤读热点**：读响应的量由请求方配额决定，属于接收方驱动；再用响应方的 CC 窗口门控，只会让本就受请求方限制的流闲置。mixedread 因此从 0.77 升到 0.91。
  - 实现中的一个坑：读响应段的类型字段是响应码，不是 READ。早期按 READ 判断读响应的代码从未生效，这也是一开始调参无效的原因。
- **v4 的严格等待**：在 79 个场景、两个种子上与 slack 0.1 对比，19 个更好、5 个更差（差 1–2 pp）。a2aread 加降 lane 从 0.886 升到 0.964；最差场景从 osub mixed F2up 的 0.891 降到 0.874。

实验否定、因而没有采用的设计：

- **第一轮已否定**：按 RTT 轮次更新、srtt 补偿、速率 pacing、全路径打标、以 TPG 为单位共享 SFQ pass。
- **本轮新否定**：
  - 按端口限制未回读字节（256/512 KB/端口）：a2aread 降到 0.62–0.78；
  - 按组归一化读配额：对 8 平面流不起作用；
  - 公平仲裁权重 1/k^α（α = 1.5 或 2）：mixed 降到 0.78–0.80；
  - SprayCC 调参（KDelay、AI、Gain、CapSlack、HyperIncrease）：读热点最多只到 0.84，根因不在参数。

  - v4 的情况：受损设备的稳态损失比下限最多高 **0.35 pp**（d2d F3far，3.5% 对 3.1%）；
  - 计入故障后最初 10 µs 时，最多高 0.6 pp（d2d F3near，3.7% 对 3.1%）。
- 第一轮"全网损失 0.1%–6%"不准确：全网损失最高为 **6.3%**，出现在 d2d 和 d2dread 的 F4，即服务器 0 的平面 3 L1 整体失效，相当于全网 1/16 的端口。

**故障瞬态**：评审担心"故障后 10 µs 才开始统计"漏掉了初期损失。实测最初 10 µs 的损失都不高于稳态损失：隔离类故障因为在途流量排空，初期反而更低；降 lane 时与稳态相同，误差在 ±0.6 pp 以内。

### 5.4 故障全过程与远端感知机制（回应评审第 3 条）

图在 `fig/ts_*.png`，采样间隔 200 ns，窗口 2 µs，FlexSpray v4 与 hash spray 对比。每张图上下三栏共用时间轴：受损设备的 payload 速率、故障平面承担的流量份额、该平面上交换机队列的峰值。

| 故障 | 远端得知 | 故障平面队列峰值（FlexSpray / spray） | 回到故障前水平 | 份额变化（FlexSpray） |
|---|---|---|---|---|
| d2d F3far（远端降 lane） | 无通知，仅靠带内信号 | 49 KB / 40 µs 内持续增长到 510 KB | FlexSpray 未积压；spray 40 µs 内不回落 | 12.5% → 9.0% |
| mixed F3far | 无通知 | 192 KB（+12 µs）/ 963 KB 且仍在增长 | FlexSpray +14 µs；spray 不回落 | 12.7% → 9.8% |
| d2d F1near（本端端口隔离） | 本端立即得知 | 29 KB / 45 KB，均未积压 | — | 12.5% → 0 |
| a2a F4（L1 失效） | t_f + 2 µs | 140 KB / 188 KB | — | 12.5% → 0，约 13 µs 排空；spray 在 40 µs 后仍为 12.5% |
| mixed F1ssd | t_f + 2 µs | 98 KB / 314 KB | — | 50% → 0；spray 为 45.6% |

**感知机制**：

- **本端端口隔离**：设备自己的端口状态，立即可知。
- **远端端口隔离与 L1 失效**：由仿真器的管理面通知（`UB_LINK_HEALTH_REMOTE_NOTIFY_NS`，默认 2 µs）告知所有端点，属于"预言机"式建模。
- **降 lane（F3）**：没有任何通知，算法也不读取仿真器中的端口速率。发送端只从带内信号感知：
  - 各 TP 实测的投递速率；
  - 读响应的回流速率；
  - CBFC credit 回流；
  - 只在最后一跳打标的 SprayCC 标记。

  交换机侧的 ADAPTIVE_RATE 读的是本交换机端口的当前速率，相当于本地链路协商的结果。
- 真实 UB 系统中远端通知的来源（管理面广播、链路伙伴报文，还是端侧超时推断）没有在仿真中实现，见 T3。

**通知时延敏感性**（种子 1）：

| 场景 | 0.5 µs | 2 µs | 10 µs | 50 µs |
|---|---|---|---|---|
| d2d F1far：效率 / 暴露量 | 0.987 / 127 KB | 0.988 / 210 KB | 0.989 / 593 KB | 0.988 / 2.6 MB |
| a2a F4 | 0.959 / 5.5 MB | 0.960 / 6.4 MB | 0.962 / 8.4 MB | 0.979 / 21.5 MB |
| mixed F4 | 0.973 / 4.1 MB | 0.979 / 4.5 MB | 0.984 / 6.7 MB | 0.985 / 18.3 MB |

在优雅隔离语义下，通知越慢，效率反而略高，因为隔离端口在被弃用之前还在工作。但暴露量随通知时延近似线性增长，到 50 µs 时是 2 µs 的 3–12 倍。所以通知时延影响的是硬断链下的损失，而不是优雅隔离下的效率。

- **控制小包**：控制小包走高优先级 VL，所有方案的 p99 时延都在 1.8–2.0 µs，不是区分点。

### 5.8 端侧代价与乱序（回应评审第 6 条）

**实测乱序**（接收端，FlexSpray v4）：

| 条件 | 最大乱序距离（PSN） | 单 TP 乱序缓存最大值 | 乱序包占比 |
|---|---|---|---|
| a2a、a2aread、d2d | 5–11 | 5–11 个包（≤ 44 KB） | 3–28% |
| mixed / mixedread | 18 / 74 | 11 / 55 个包 | 7–9% |
| incast | 25 | 18 个包 | 12% |
| 浅缓冲下的 mixedread（最坏） | 127 | 109 个包（约 440 KB） | 10% |

对比：spray 在 incast 下乱序距离 324、缓存 221 个包；在浅缓冲 mixedread 下为 493 / 438。

现有 TP 乱序窗口为 8192 PSN，所有 case 都远未触及。

**FlexSpray 新增的端侧状态**（每个 TP）：

| 项目 | 大小 |
|---|---|
| SFQ pass | 8 B |
| 投递速率估计 | 约 24 B |
| 未回读字节 | 8 B |
| SprayCC 速率、α、计数等 | 约 48 B |
| 发送记录环（psn, size, time） | 每个在途包 16 B；在途上限约为线速 × 10 µs / 4 KB ≈ 122 包，即每 TP ≤ 2 KB |

一个 alltoall 中的 NPU 有 31 × 8 = 248 个 TP：新增常驻状态约 22 KB，发送记录环最坏约 0.5 MB。

**每包和每 segment 的操作**：

- 主机每端口每发一包：在活跃 TP 中做一次 SFQ 选择，用堆实现为 O(log n)，n ≤ 248。在 400G、4 KB 包的条件下约 82 ns 一包。
- 每个 16 KB segment：做一次 ≤ 8 个候选的 argmin，在 400G 下约每 330 ns 一次。
- 交换机每包：对 ≤ 12 个候选出口比较 (队列 + 下游 credit 占用) / 速率，可用交叉相乘代替除法。所需计数器 CBFC 已经维护。
- 最后一跳打标：每包一次比较。

**无法在当前环境核实的**：

- 真实交换机的仲裁方式。仿真器默认按输入端口轮询，第一轮把部分基线的 alltoall 长尾归因于此。
- 上述操作在目标网卡或 NPU 上的实现代价。

见 T4。

## 6. 仿真器问题与修复

第一轮的提速与 bug 修复不再重复，见提交记录。本轮新增：

1. **CBFC 配置陷阱**：credit 回送阈值（默认 1024 cell）大于初始 credit 时，单向流量的 credit 永远收不回来，链路静默死锁。在做 128 KB 缓冲实验时遇到。现在初始化时会告警；不改成中止，是因为有单元测试故意使用很小的 credit。
2. **读请求可以走单独的 VL**：接收端查找 TP 时按优先级匹配。现在只对确有 TP 使用的读请求 VL 放宽这一匹配，"优先级不匹配应中止"的原有不变量测试仍然通过。
3. **采样器新增列**：`GoodputSample.csv` 新增 queue_bytes、fc_blocked_ns、ooo_pkts、max_reorder_psn、max_ooo_buffered。一个按 8 列解析该文件的测试已改为 ≥ 8 列。
4. **第一轮报告的一处标注错误**：消融表中"去掉分发等待（slack）"那一行，实际配置是 `TpgDispatchSlack=0`，即最严格的等待，而不是关闭等待（负值才是关闭）。本轮消融把这两种分开测了。

验证：每次改动后，scratch 下的 24 个 case 加上 2 个大型 alltoall 的 runlog 均与基线逐字节一致；50 个 unified-bus 测试套件全部通过。新增的属性默认值都保持原有行为。

## 7. 局限

- **故障语义**：仍是"优雅隔离"。本轮用暴露量刻画了硬断链下会受影响的字节数，读场景的暴露量很大。真实的硬断链需要 TA 级跨 TP 重发，见 T1。
- **远端通知**：由仿真器的管理面通知，时延可配，见 T3。
- **测试条件**：没有使用题目指定的 benchmark 与拓扑（T2）；规模为 48 端点（T5）。
- **未达标项**：上行收敛 fabric 加上行口隔离时混跑为 0.874（T10）；mixedread 中最差 NPU 的全程利用率为 0.883，稳态为 0.982。
