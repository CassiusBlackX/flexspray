多平面超节点下的流量均衡与网络无拥塞保障挑战

一、技术背景

UB 支持计算设备、网络设备、存储设备等多类设备的全池化互联。不同设备可能具有不同的端口带宽、接入平面数量与通信模式。

在超节点中，设备间通信、主机与设备间通信、跨主机设备访问，以及计算设备直接访问存储或网络设备等业务，共享相同的物理链路。集合通信、点对点传输、存储读写与控制小包同时运行时，容易发生局部流量冲突，并通过排队和反压影响其他业务。

多平面组网进一步增加了动态均衡的难度。不同设备可使用的平面数量不一致，通信双方能够共同使用的路径集合也可能不同。即使网络总容量充足，分配不合理仍可能造成部分端口拥塞、其他端口空闲。

此外，故障保护可能触发端口隔离或 Lane 降级，造成路径容量不对称。网络需要根据可用容量与拥塞状态动态调整流量分配，在复杂混跑和链路亚健康状态下保持较高的带宽利用率。


二、技术挑战

1. 复杂业务混跑

需要支持环形集合通信、多对多通信、alltoall、KVCache 读写和控制小包等业务。不同业务在报文大小、读写方向、并发规模和突发程度上存在差异，容易形成动态热点与局部拥塞。

2. 多平面动态均衡

平面故障或路径容量下降后，需要及时感知变化并重新分配流量，避免继续向慢路径积压工作，减少完成时间拖尾。

3. 异构可达路径约束

计算设备、网络设备和存储设备具有不同的端口数量、平面数量和带宽。方案需要在通信双方实际可达的路径集合内实现有效分担，避免平面较少的设备或业务受到不合理挤压。

4. 逐包喷洒与拥塞控制协同

Packet Spray 会产生乱序，局部慢路径可能影响累计确认、反馈及时性与完成时间。需要准确识别拥塞、容量下降和真实丢包，避免无效降速、误重传及其引起的拥塞放大。


三、技术目标与功能要求

基于 UB 多平面全池化组网，设计并实现采用 Packet Spray 的负载均衡与拥塞控制方案，支持：

（1）逐包负载分担；
（2）多平面之间的负载分担；
（3）多端口之间的负载分担；
（4）适应异构设备的带宽与可达平面差异；
（5）根据拥塞、故障和路径容量变化动态调整分配；
（6）保障读写完成语义和故障恢复正确性。

方案应兼顾健康状态的吞吐与故障状态的恢复，不能通过牺牲某类业务、无限增加缓存或依赖不可实现的全局信息获得表面收益。


四、性能要求

1. 跨主机点对点通信

对于设备间、主机与设备间，以及计算设备与网络或存储设备间的跨主机点对点通信，带宽利用率达到带宽上限的 95%。

2. 集合通信

对于 alltoall，带宽利用率达到带宽上限的 90%。

3. 混合业务

在 alltoall 与点对点通信混合运行时，计算设备、其他异构设备及存储设备的端口带宽利用率均达到带宽上限的 90%。

同时增加存储热点、读写混合和控制小包，验证复杂混跑下的性能与业务间影响。

4. 故障与链路降级

发生端侧单平面故障、交换侧单端口故障或单端口 Lane 降级时，整网设备应快速重新均衡，通信带宽损失满足：

    带宽损失 < 1/N

其中，N 为平面数或总 Lane 数。

需要覆盖近端与远端故障、读与写方向，以及点对点、集合通信和混合业务。

必须保留上述原始目标。对于 N 的不同解释、故障语义或指标窗口，应明确列出，不得自行选择最宽松的解释后宣称全部达标。

如果某项要求在具体流量和容量约束下不可实现，应给出可核对的容量分析或求解证据，并区分物理限制、协议限制和实现不足。不能仅以当前方案表现不佳推断目标不可实现。
