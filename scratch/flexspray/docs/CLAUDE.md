## 1. 目标

- **主目标**：满足 REQUESTS.md 中功能 (1)–(6) 和性能 1–4 的原始硬指标。
  - 不改写指标，也不自选最宽松的口径；
  - 不得用牺牲某类业务、无限增加缓存或依赖不可实现的全局信息来换取表面上的达标。
- **副目标（记录即可，不主动追逐）**：一旦出现可推广的发现，立即记到 `scratch/flexspray/RESEARCH.md` 的"贡献候选"一节，写明：
  - 现象；
  - 证据目录；
  - 可被推翻的检验；
  - 与已读文献的差别。

  "可推广的发现"包括：新的问题刻画、上界或不可行性证明、有原则的机制，以及显著优于已有方案的结果。
- 两者冲突时，以诚实、可复核为先。宁可报告"某项不可达（附证明）"，也不报告"全部达标"。

## 3. 硬规则

### 正确性优先
- 功能 (6) 要求读写完成语义和故障恢复正确。**挂死、缺任务、提前完成**都是 P0，优先于任何性能工作。
- 每个候选版本都要通过以下全部检查：
  - golden：默认配置下逐位相同；
  - 50 个 `unified-bus` 单测套件，**顺序执行**；
  - 恢复预言机：`flexspray_regress.py`、`FLEX_DRAIN_AFTER_US=200`；
  - 硬故障矩阵：无挂死。

### 构建
- 单测运行期间不得改 C++：examples 套件会重建共享库。
- 改了头文件后，冻结前必须同时重建 `unified-bus-test` 和 `test-runner`。
- 矩阵在跑时，不要重建它正在使用的构建。
- 同一时间只跑一个 build。

### 进程
- 等待完成时看日志里的 `ALLDONE` 标记。不要用 `pgrep -f` / `pkill -f` 匹配命令行：它们会匹配到自己的 shell。
- 分析脚本设 `OMP_NUM_THREADS=1`，按 case 并行；LP 用 `highs-ipm`。

### 盲测
- 只用种子 1、2 调参。
- 验收必须用从未用过的样本。已用过的样本列在 `EVAL_PROTOCOL.md`，每次新用都要追加。

### 默认配置升级
- 新机制必须附消融。
- 相对研究对照基线和当前默认配置，核心、降 lane、硬故障矩阵以及未见集上，任何一行都不得差超过 1 pp。
- 不达标的机制只能作为默认关闭的选项存在。

### 控制复杂度
- 不要为单个失败行新增开关。新增开关之前，先说明它对应哪一条一般原则。
- 被否定的开关要删除其代码路径，用标签保留历史即可。

### 结论标签
- 每条结论标注以下之一：【已实现并验证】【有限条件下成立】【仍是假说】【未解决】。
- 评价器（分析脚本）的修正单独提交，并且对新旧版本用同一个评价器重算。

### 永远不要声称
- 远端执行恰好一次；
- 严格 < 1/N 全部达标；
- 测试范围以外"无误判"；
- 由自定义负载得出的"真实场景"结论。

## 4. 指标口径：全部并列报告

REQUESTS 要求把 N 的不同解释、故障语义和指标窗口都**列出来**。报告"故障损失"时，下面每一维的每个取值都要给出：

| 维度 | 必须并列的取值 |
|---|---|
| N | (a) 受损设备的平面数 N_dev<br>(b) 受损设备的总 lane 数 4·N_dev<br>(c) 故障作用域内的平面数<br>(d) 容量感知界（LP 最小损失） |
| 损失窗口 | (i) 重均衡后的稳态带宽：受损设备在故障后稳定窗口内的带宽，对比健康运行的同一窗口<br>(ii) 受损设备的完成时间 / makespan<br>(iii) 故障后最初的瞬态 |
| 故障语义 | 优雅隔离（管理面通知）、硬断链、降 lane（x4→x3/x2/x1）分开报告 |
| 关系 | 原文是 "<"；"≤" 只能作为附加列 |

- **重均衡时间**单独报告：从故障到恢复至新稳态 95% 所用的时间。
- **不可达**必须附证据，并说明属于哪一类：
  - 物理限制：逐设备 LP 不可行，给出容量割；
  - 协议限制：例如承诺上限；
  - 实现不足。
- 不能凭"当前方案做不到"就推断不可达。
