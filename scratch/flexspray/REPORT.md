## 2. 实验平台与条件

拓扑与第一轮相同（`flexspray_case.py`）：

- 4 台服务器，共 48 个端点、64 台交换机，8 个平面，端口为 400G（4 lane）。
- 每个平面是独立的 2 层 Clos，每个 L1 有 12 条上行、最多 11 条下行，无阻塞。
- CBFC 无损，关闭重传，TPACK 走 VL1。

本轮新增的条件：

| 类别 | 新增内容 |

| 场景 | `a2aread`：32 个 NPU 互相 URMA_READ |
| | `mixedread`：读主导的混跑。alltoall 改为读；NPU4/5 从 SSD0 读 KVCache，使 SSD0 的出口成为热点 |
| | `stagger`、`staggermixed`：流大小在 0.25–2 倍之间对数均匀分布，按 8 档、每档 5 µs 错峰启动 |

## 3. 指标口径（本轮重新定义）

**效率**：效率 = T_ideal / 实测 makespan，两个种子取较差的一个。T_ideal 由流体 LP 求出：

- 流可以在共有平面上任意拆分；端口容量按线上字节计，数据为 (4096+78)/4096，ACK 为 62–70 B/包；同时约束 L1 的上行和下行汇聚容量。
- **与"优雅隔离"保持一致**：仿真中被隔离端口上的已排队和在途流量会照常排空。对每个被隔离的资源，LP 允许它在 t_f 之后承载与仿真实测相同的排空字节数。修正前，有 18 个 case 的效率大于 1；修正后没有。
- **错峰启动**：LP 按 {0, 各流释放时间, t_f} 分段求解，结果精确；对没有释放时间的 case，与原 LP 结果完全一致。

**逐设备端口利用率**（`flexspray_portutil.py`），对每个设备、每个方向分别计算：

- 分子：实测的 TP payload 速率，只统计该设备在这个方向上实际承载流量的端口。
- 分母（协议上限）：Σ 端口 (当前速率 × 时长 − 本端口上的非数据字节) / 数据开销系数。
  - 非数据字节包括反向 ACK 和 credit 帧，按实测扣除；
  - 降 lane 按降级后的速率积分；
  - 被隔离的端口在 t_f 后只计它实际排空的字节；
  - 每个平面的上限再与对端端口的可达容量取较小值，例如对端被隔离时该平面上限为 0。
- 两个时间窗口：
  - **全程**：设备自己的忙碌期 [0, 最后一条流完成]，包含启动和尾段，口径最严格；
  - **稳态**：[10 µs, 0.95 × 首条流完成]，故障场景再拆成故障后稳态 [t_f+10 µs, …] 和故障瞬态 [t_f, t_f+10 µs]。
- 另报两种口径：payload / 线速（约等于协议利用率 × 0.96）、线上利用率。
- **需求检查**：需求 = 设备字节数 / 无故障时的 T_ideal。核心场景中所有设备的需求都 ≥ 0.9 × 端口上限，没有"需求很少所以看起来效率高"的设备，因此评审担心的那种情况不存在。错峰和 incast 场景按设计不饱和，不进逐设备表。

**故障损失**：

- 计算方式：1 − 受损设备带宽 / 同一方案无故障运行时的带宽，取三个窗口：稳态 [t_f+10, end]、全程 [t_f, end]、最初 10 µs [t_f, t_f+10]。
- 对比的物理下限不再用 1/N，而是**实际被移除的容量占比**：受损设备实际承载流量的平面数中被去掉的份额，降 lane 按 1/lane 计。
  - 例如 h2d 场景中 NPU6 只用 6 个平面，下限为 1/6；F4p4 涉及多个设备，按容量加权。

**暴露量**：t_f 之后仍然经过被隔离资源的线上字节数及持续时间。它是硬断链的代理指标：换成突然断链，这些字节会丢失并需要重发。

**拥塞与开销**（采样器新增的列）：

- 交换机输出队列（VOQ + egress）的峰值和均值；
- CBFC 因缺 credit 而阻塞的时间占比；
- 控制小包 p99 时延；
- 接收端乱序距离（PSN），以及每个 TP 乱序缓存的最大包数。

## 4. FlexSpray 设计（v4）

| 层 | 机制 | 版本 |
|---|---|---|
| 交换层 | `ADAPTIVE_RATE`：逐包选 (VOQ + egress + 下游已消耗 credit) / 端口当前速率最小的出口 | v1 |
| 端侧仲裁 | `TpGroupFairShare`：主机出口在各 TP 间做 SFQ，权重为 1/k，k 为该流的平面数。**v3 改为只计未被隔离的平面**（`TpGroupFairShareUsableOnly`） | v1 / v3 |
| 端侧分发 | `MIN_DRAIN_TIME`：segment 分给"(未发 + 在途 + 未回的读响应) / 实测投递速率"最小的平面。**v4 采用严格等待**（`TpgDispatchSlack=0`）：只要最好的可用平面比最好的平面慢就等待。segment 为 16 KB | v1 / v4 |
| 读路径 | 每个 TP 的读配额为 192 KB | v1 |
| | 读请求和读响应有单独的发送管线深度，为 8（`MaxActiveReadSegments`） | v2 |
| | 读请求走控制 VL（`ReadRequestVl=1`） | v3 |
| | 流失去平面后，读配额重新分摊到剩余平面（`ReadQuotaFollowsUsablePlanes`） | v3 |
| | 读响应不受 SprayCC 窗口门控（`CcExemptReadResponses`） | v3 |
| 拥塞控制 | SprayCC：只在最后一跳打标（排队 > 2 µs）；接收端统计 marked/total；每 2 µs 一个固定周期做 DCTCP 式降速；同一 TPG 内各 TP 耦合加速；在途上限为 rate × (baseRTT + 8 µs) | v1 |

v3 各项改动的动机，均来自本轮新覆盖暴露出的根因：

- **读请求被浅管线卡住**：发送管线深度 2 × 16 KB 同时限制了读请求，导致 a2aread 只有 0.79。读的接纳本来就由读配额约束，响应走哪个平面也由请求决定，所以给读单独一个更深的管线，不会损失分发的灵活性。
- **读请求排在 incast 数据后面**：读请求虽然很小，但在 SSD0 被打满的入口上排在 incast 数据后面，拉长了每次读的往返时间。改走控制 VL 后：F3ssd 从 0.866 升到 0.935（单种子，下同）；加上配额重新分摊和按可用平面计权，F1ssd 从 0.807 升到 0.956，F4p4 从 0.807 升到 0.951。
- **SprayCC 误伤读热点**：读响应的量由请求方配额决定，属于接收方驱动；再用响应方的 CC 窗口门控，只会让本就受请求方限制的流闲置。mixedread 因此从 0.77 升到 0.91。
  - 实现中的一个坑：读响应段的类型字段是响应码，不是 READ。早期按 READ 判断读响应的代码从未生效，这也是一开始调参无效的原因。
- **v4 的严格等待**：在 79 个场景、两个种子上与 slack 0.1 对比，19 个更好、5 个更差（差 1–2 pp）。a2aread 加降 lane 从 0.886 升到 0.964；最差场景从 osub mixed F2up 的 0.891 降到 0.874。

实验否定、因而没有采用的设计：

- **第一轮已否定**：按 RTT 轮次更新、srtt 补偿、速率 pacing、全路径打标、以 TPG 为单位共享 SFQ pass。
- **本轮新否定**：
  - 按端口限制未回读字节（256/512 KB/端口）：a2aread 降到 0.62–0.78；
  - 按组归一化读配额：对 8 平面流不起作用；
  - 公平仲裁权重 1/k^α（α = 1.5 或 2）：mixed 降到 0.78–0.80；
  - SprayCC 调参（KDelay、AI、Gain、CapSlack、HyperIncrease）：读热点最多只到 0.84，根因不在参数。

- 第一轮"所有故障损失都等于物理下限，误差 ≤0.4pp"不准确：v1 的 d2dread F3far 损失为 4.2%，比下限高 1.1 pp。

  - 计入故障后最初 10 µs 时，最多高 0.6 pp（d2d F3near，3.7% 对 3.1%）。
- 第一轮"全网损失 0.1%–6%"不准确：全网损失最高为 **6.3%**，出现在 d2d 和 d2dread 的 F4，即服务器 0 的平面 3 L1 整体失效，相当于全网 1/16 的端口。

**故障瞬态**：评审担心"故障后 10 µs 才开始统计"漏掉了初期损失。实测最初 10 µs 的损失都不高于稳态损失：隔离类故障因为在途流量排空，初期反而更低；降 lane 时与稳态相同，误差在 ±0.6 pp 以内。

### 5.4 故障全过程与远端感知机制（回应评审第 3 条）

图在 `fig/ts_*.png`，采样间隔 200 ns，窗口 2 µs，FlexSpray v4 与 hash spray 对比。每张图上下三栏共用时间轴：受损设备的 payload 速率、故障平面承担的流量份额、该平面上交换机队列的峰值。

| 故障 | 远端得知 | 故障平面队列峰值（FlexSpray / spray） | 回到故障前水平 | 份额变化（FlexSpray） |
|---|---|---|---|---|
| d2d F3far（远端降 lane） | 无通知，仅靠带内信号 | 49 KB / 40 µs 内持续增长到 510 KB | FlexSpray 未积压；spray 40 µs 内不回落 | 12.5% → 9.0% |
| mixed F3far | 无通知 | 192 KB（+12 µs）/ 963 KB 且仍在增长 | FlexSpray +14 µs；spray 不回落 | 12.7% → 9.8% |
| d2d F1near（本端端口隔离） | 本端立即得知 | 29 KB / 45 KB，均未积压 | — | 12.5% → 0 |
| a2a F4（L1 失效） | t_f + 2 µs | 140 KB / 188 KB | — | 12.5% → 0，约 13 µs 排空；spray 在 40 µs 后仍为 12.5% |
| mixed F1ssd | t_f + 2 µs | 98 KB / 314 KB | — | 50% → 0；spray 为 45.6% |

**感知机制**：

- **本端端口隔离**：设备自己的端口状态，立即可知。
- **远端端口隔离与 L1 失效**：由仿真器的管理面通知（`UB_LINK_HEALTH_REMOTE_NOTIFY_NS`，默认 2 µs）告知所有端点，属于"预言机"式建模。
- **降 lane（F3）**：没有任何通知，算法也不读取仿真器中的端口速率。发送端只从带内信号感知：
  - 各 TP 实测的投递速率；
  - 读响应的回流速率；
  - CBFC credit 回流；
  - 只在最后一跳打标的 SprayCC 标记。

  交换机侧的 ADAPTIVE_RATE 读的是本交换机端口的当前速率，相当于本地链路协商的结果。
- 真实 UB 系统中远端通知的来源（管理面广播、链路伙伴报文，还是端侧超时推断）没有在仿真中实现，见 T3。

**通知时延敏感性**（种子 1）：

| 场景 | 0.5 µs | 2 µs | 10 µs | 50 µs |
|---|---|---|---|---|
| d2d F1far：效率 / 暴露量 | 0.987 / 127 KB | 0.988 / 210 KB | 0.989 / 593 KB | 0.988 / 2.6 MB |
| a2a F4 | 0.959 / 5.5 MB | 0.960 / 6.4 MB | 0.962 / 8.4 MB | 0.979 / 21.5 MB |
| mixed F4 | 0.973 / 4.1 MB | 0.979 / 4.5 MB | 0.984 / 6.7 MB | 0.985 / 18.3 MB |

在优雅隔离语义下，通知越慢，效率反而略高，因为隔离端口在被弃用之前还在工作。但暴露量随通知时延近似线性增长，到 50 µs 时是 2 µs 的 3–12 倍。所以通知时延影响的是硬断链下的损失，而不是优雅隔离下的效率。

- **分工**：无拥塞树的场景（a2a、d2d、mixed 写）主要靠分发和公平仲裁，SprayCC 的增减在 ±1 pp 以内。

- **控制小包**：控制小包走高优先级 VL，所有方案的 p99 时延都在 1.8–2.0 µs，不是区分点。

### 5.8 端侧代价与乱序（回应评审第 6 条）

**实测乱序**（接收端，FlexSpray v4）：

| 条件 | 最大乱序距离（PSN） | 单 TP 乱序缓存最大值 | 乱序包占比 |
|---|---|---|---|
| a2a、a2aread、d2d | 5–11 | 5–11 个包（≤ 44 KB） | 3–28% |
| mixed / mixedread | 18 / 74 | 11 / 55 个包 | 7–9% |
| incast | 25 | 18 个包 | 12% |
| 浅缓冲下的 mixedread（最坏） | 127 | 109 个包（约 440 KB） | 10% |

对比：spray 在 incast 下乱序距离 324、缓存 221 个包；在浅缓冲 mixedread 下为 493 / 438。

现有 TP 乱序窗口为 8192 PSN，所有 case 都远未触及。

**FlexSpray 新增的端侧状态**（每个 TP）：

| 项目 | 大小 |
|---|---|
| SFQ pass | 8 B |
| 投递速率估计 | 约 24 B |
| 未回读字节 | 8 B |
| SprayCC 速率、α、计数等 | 约 48 B |
| 发送记录环（psn, size, time） | 每个在途包 16 B；在途上限约为线速 × 10 µs / 4 KB ≈ 122 包，即每 TP ≤ 2 KB |

一个 alltoall 中的 NPU 有 31 × 8 = 248 个 TP：新增常驻状态约 22 KB，发送记录环最坏约 0.5 MB。

**每包和每 segment 的操作**：

- 主机每端口每发一包：在活跃 TP 中做一次 SFQ 选择，用堆实现为 O(log n)，n ≤ 248。在 400G、4 KB 包的条件下约 82 ns 一包。
- 每个 16 KB segment：做一次 ≤ 8 个候选的 argmin，在 400G 下约每 330 ns 一次。
- 交换机每包：对 ≤ 12 个候选出口比较 (队列 + 下游 credit 占用) / 速率，可用交叉相乘代替除法。所需计数器 CBFC 已经维护。
- 最后一跳打标：每包一次比较。

**无法在当前环境核实的**：

- 真实交换机的仲裁方式。仿真器默认按输入端口轮询，第一轮把部分基线的 alltoall 长尾归因于此。
- 上述操作在目标网卡或 NPU 上的实现代价。

见 T4。

## 6. 仿真器问题与修复

第一轮的提速与 bug 修复不再重复，见提交记录。本轮新增：

1. **CBFC 配置陷阱**：credit 回送阈值（默认 1024 cell）大于初始 credit 时，单向流量的 credit 永远收不回来，链路静默死锁。在做 128 KB 缓冲实验时遇到。现在初始化时会告警；不改成中止，是因为有单元测试故意使用很小的 credit。
2. **读请求可以走单独的 VL**：接收端查找 TP 时按优先级匹配。现在只对确有 TP 使用的读请求 VL 放宽这一匹配，"优先级不匹配应中止"的原有不变量测试仍然通过。
3. **采样器新增列**：`GoodputSample.csv` 新增 queue_bytes、fc_blocked_ns、ooo_pkts、max_reorder_psn、max_ooo_buffered。一个按 8 列解析该文件的测试已改为 ≥ 8 列。
4. **第一轮报告的一处标注错误**：消融表中"去掉分发等待（slack）"那一行，实际配置是 `TpgDispatchSlack=0`，即最严格的等待，而不是关闭等待（负值才是关闭）。本轮消融把这两种分开测了。

验证：每次改动后，scratch 下的 24 个 case 加上 2 个大型 alltoall 的 runlog 均与基线逐字节一致；50 个 unified-bus 测试套件全部通过。新增的属性默认值都保持原有行为。

## 7. 局限

- **故障语义**：仍是"优雅隔离"。本轮用暴露量刻画了硬断链下会受影响的字节数，读场景的暴露量很大。真实的硬断链需要 TA 级跨 TP 重发，见 T1。
- **远端通知**：由仿真器的管理面通知，时延可配，见 T3。
- **测试条件**：没有使用题目指定的 benchmark 与拓扑（T2）；规模为 48 端点（T5）。
- **未达标项**：上行收敛 fabric 加上行口隔离时混跑为 0.874（T10）；mixedread 中最差 NPU 的全程利用率为 0.883，稳态为 0.982。
