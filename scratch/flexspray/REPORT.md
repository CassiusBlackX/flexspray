## 1. 结论速览

| 指标（需求） | 目标 | FlexSpray（2 个种子均值） | 最好的对照方案 |
|---|---|---|---|
| D2D 跨机点对点写 | ≥95% | **98.6%** | hash spray 99.3% |
| D2D 跨机点对点读 | ≥95% | **98.8%** | hash spray 99.7% |
| H2D/RH2D/D2H/NIC/KV 异构点对点 | ≥95% | **98.3%** | static 98.8% |
| alltoall（32 NPU，全部并发） | ≥90% | **96.4%** | static 91.8%，其余 82–90% |
| alltoall + 点对点 + 存储 incast + 控制小包混跑 | 各类设备均 ≥90% | **NPU 92.5% / CPU 98.2% / NIC 98.6% / SSD 92.5%** | hash spray 66%，UB adaptive+CAQM 67%，spray+DCQCN 60%，ECMP+DCQCN 52% |
| 单平面/单端口隔离、单 Lane 降级、单平面 L1 失效 | 损失 < 1/N | **损失 = 被移除的容量**，见第 5 节 | 部分对照方案出现损失放大，或在故障后长尾 |

表中百分比的口径均为"效率 = 理论最优完成时间 / 实测完成时间"，定义见第 3 节。这是协议层上限口径，已经计入 78B 包头和反向 ACK 的开销。

关于第三项指标，有两点需要如实说明：
- 当受损设备本身就是瓶颈时，任何方案的损失都不可能小于被移除的容量。例如 8 个平面坏 1 个，损失至少 1/8。
- FlexSpray 在所有故障场景下，受损设备的损失都等于物理下限（误差 ≤0.4pp），没有放大；全网损失在 0.1%–6% 之间，远小于 1/N。
- 按"严格小于 1/N"的字面理解，只有故障不在瓶颈上的场景能满足。例如 L1 上行口隔离（F2）损失为 0。

## 2. 实验平台与条件

数据中心级超节点规模、异构设备、多平面，见 `scratch/flexspray/flexspray_case.py`。

| 项目 | 设定 |
|---|---|
| 服务器 | 4 台 |
| 每台设备 | 8×NPU（8 平面，每端口 400G = 4 lane×100G）、2×CPU（平面 0–3）、1×NIC（平面 0–1）、1×SSD（平面 4–5） |
| 端点 / 交换机 | 共 48 个端点、64 台交换机 |
| 每个平面 | 每台服务器 1 个 L1，另有 4 个 L2；每对 L1–L2 有 3 条并行链路，即每个 L1 有 12 条上行（≥ 最大 11 条下行），无阻塞 |
| 时延 | 主机–L1 链路 20 ns，L1–L2 链路 100 ns，交换机转发 100 ns，分配 1 ns；基础 RTT 约 0.6 µs（同服务器）到 1.6 µs（跨服务器） |
| 流控与重传 | CBFC 无损，关闭重传；所有方案相同 |
| 端侧传输 | RTP，多 TP（TPG），主机路由按平面绑定，所以 TPG 天然按平面匹配：CPU↔NPU 只用两者共有的 4 个平面 |
| ACK 优先级 | TPACK 走更高优先级的 VL1，所有方案一致（原因见第 6 节） |

负载设计：每条流的大小 = 设计速率 × 160 µs，理想情况下所有流同时完成。

| 场景 | 内容 |
|---|---|
| `d2d` | 32 个 NPU 跨服务器置换写，每对 64 MB |
| `d2dread` | 同 `d2d`，但为 `URMA_READ` |
| `h2d` | 端点互不重叠的异构点对点：CPU0→NPU6（H2D）、CPU1→远端 NPU7（RH2D）、NPU6→CPU1（D2H）、NIC→CPU0、NPU7→NIC、NPU6 从远端 SSD 读 KVCache、NPU7 写 SSD |
| `a2a` | 32 个 NPU 全对全，所有发送并发，不按 phase 分轮，与集合通信库的行为一致 |
| `mixed` | NPU0–5 共 24 个之间做 alltoall，叠加 `h2d` 全套，叠加 6 个 NPU 对 SSD0 的 KVCache 写 incast（只走平面 4–5），再叠加高优先级 256B 控制小包 |

故障注入在 t = 50 µs，均作用于平面 3：

| 编号 | 故障 |
|---|---|
| F1near / F1far | 发送端 / 接收端设备的该平面端口被隔离（读场景中两端方向相反） |
| F2up | 一条 L1 上行口被隔离 |
| F3near / F3far | 近端 / 远端端口降 1 个 lane（400G→300G） |
| F4 | 服务器 0 的平面 3 L1 交换机整体隔离 |

对照方案（参数均经过小范围调优；DCQCN 从 3 套参数中选了最好的 `dq2`）：

| 名称 | 含义 |
|---|---|
| `ecmp` | 端侧多 QP（TPG 先空先发）＋平面内逐流 ECMP，即 RDMA 逐流均衡 |
| `ecmp+dq2` | 同上，再加 DCQCN（LineRate 400G，Kmin/Kmax 100/400 KB，Pmax 0.2，2 µs 定时器） |
| `static` | 静态轮询多 QP 切分 |
| `spray` / `spray+dq2` | 逐包 hash 喷洒 ± DCQCN（Packet Spray + DCQCN） |
| `adaptive+caqm` | UB 仓库现有能力：逐包按本地队列字节自适应 ＋ C-AQM |

## 3. 指标口径

- **理论上限 T_ideal**：一个流体 LP。所有流可在共有平面上任意分配。端口容量约束按线上字节计：数据为 (4096+78)/4096，ACK 为 62–70 B/4096。约束还包括 L1 上下行汇聚容量。有故障时把 [0, t_f) 和 [t_f, T) 分两段容量，合成一个 LP 直接求最小 T。
- **效率** = T_ideal / 实测 makespan。对单个设备，效率 = T_ideal / 该设备最后一条流的完成时间。混跑场景的"各类设备 ≥90%"就是按这个逐设备计算的。
- **故障损失** = 1 − BW_fault / BW_healthy。取受损设备在故障后稳态窗口 [t_f+10 µs, …] 内的 payload 吞吐，与同一方案、同一时间窗的无故障运行对比；同时给出全网损失。
- **N**：设备实际承载流量的平面数（或 lane 数）。NPU 为 8 平面 / 32 lane，CPU 为 4 平面 / 16 lane。

## 4. FlexSpray 设计

| 层 | 机制 | 解决的问题 |
|---|---|---|
| 交换层 | `MultipathSelector=ADAPTIVE_RATE`：逐包选择 (VOQ + egress + 由已消耗 CBFC credit 推出的下游积压) / 端口**当前**速率最小的出口 | 降 lane 口按字节会被低估；能看到下一跳拥塞 |
| 端侧仲裁 | `TpGroupFairShare`：主机出口在各 TP 间做 SFQ，权重为 1/(TPG 平面数) | 平面受限设备（CPU 4 平面、SSD/NIC 2 平面）与 8 平面 alltoall 共用端口时，按流而不是按 TP 公平。**这是混跑达标的关键** |
| 端侧分发 | `MIN_DRAIN_TIME`：segment 分给"(未发 + 在途 + 未回的读响应) / 实测投递速率"最小的平面；`TpgDispatchSlack=0.1`：若最好的可用平面比最好的平面慢 10% 以上就等待，不硬塞；segment 缩到 16 KB | 跨平面逐包级负载分担；故障平面、降速平面、远端拥塞平面自动少分 |
| 读流量 | `MaxOutstandingReadBytes=192 KB`：每个 TP 未回读响应字节上限 | 远端响应方降速时，请求方不再向该平面无限发读请求 |
| 拥塞控制 | `UB_CC_ALGO=SPRAYCC` | 见下方要点 |

SprayCC 的要点：
- **打标**：只在面向设备的最后一跳打标（edge-only），条件是排队时延（按端口当前速率换算）> 2 µs。
- **反馈**：接收端统计 marked/total（乱序包也计入），随累计 ACK 的 CETPH 回传。
- **发送端控制**：每 2 µs 一个固定周期，采用 DCTCP 式 α 降速；同一 TPG 内各 TP 耦合加速，组总增量按各平面速率份额分配；在途字节上限为 rate×(baseRTT+8 µs)。

实现中被实验否定、因而没有采用的设计：
- **按 RTT 轮次更新**：同服务器流与跨服务器流 RTT 不同，造成不公平。
- **按 srtt 做 RTT 补偿**：队列越大加速越快，形成正反馈。
- **速率 pacing**：alltoall 场景下 248 个 TP 同时以线速起步，导致拥塞扩散，效率只有 33%。
- **全路径打标**：多跳流被重复惩罚（parking-lot 问题）。
- **以 TPG 为单位共享 SFQ pass**：同一流的包在各端口上被串行化，多个接收端同步受冲击，alltoall 效率降到 79%。

## 5. 主要结果

### 5.1 无故障效率（2 个种子均值）

| 方案 | d2d | d2dread | h2d | a2a | mixed |
|---|---|---|---|---|---|
| **flex+spraycc** | **0.986** | **0.988** | **0.983** | **0.964** | **0.925** |
| adaptive+caqm | 0.983 | 0.957 | 0.981 | 0.817 | 0.667 |
| ecmp | 0.445 | 0.254 | 0.986 | 0.888 | 0.642 |
| ecmp+dq2 | 0.438 | 0.213 | 0.978 | 0.885 | 0.518 |
| spray | 0.993 | 0.997 | 0.986 | 0.898 | 0.660 |
| spray+dq2 | 0.993 | 0.998 | 0.980 | 0.861 | 0.596 |
| static | 0.252 | 0.254 | 0.988 | 0.918 | 0.634 |

- 逐流 ECMP 和静态切分在 d2d 下因 hash 冲突，或者"最慢的 QP 决定整体完成时间"，只有 25–45%。
- 无故障的纯点对点场景中，逐包 hash spray 已经足够好。
- 差距出在 alltoall 和混跑：
  - 对照方案 alltoall ≤ 92%，原因是交换机按输入端口轮询仲裁，同服务器流和跨服务器流不公平，导致长尾；
  - 对照方案混跑 ≤ 67%，原因是 KV incast 的 2 平面流在发送端口上只能拿到 1/24 的份额；
  - DCQCN 在这个规模和 µs 级 RTT 下明显拖累性能。

### 5.2 故障（FlexSpray，2 个种子均值）

每格依次为：效率 / 受损设备损失（括号内为 1/N）/ 全网损失。

| 场景 | F1near | F1far | F2up | F3near | F3far | F4 |
|---|---|---|---|---|---|---|
| d2d | 0.989 / 12.5%（12.5%）/ 0.8% | 0.989 / 12.5% / 0.8% | 0.986 / 0.0%（8.3%）/ 0.0% | 0.985 / 3.1%（3.1%）/ 0.2% | 0.985 / 3.3% / 0.2% | 0.988 / 12.5% / 6.3% |
| d2dread | 0.992 / 12.5% / 0.8% | 0.991 / 12.5% / 0.9% | 0.988 / 0.0% / 0.0% | 0.983 / 3.5% / 0.2% | 0.983 / 4.2% / 0.2% | 0.991 / 12.5% / 6.7% |
| h2d | 0.991 / 25.0%（CPU，N=4）| 0.990 / 16.6%（NPU6 只用 6 个平面，=1/6） | 0.983 / 0.0% | 0.990 / 5.9%（CPU，N=16 lane，6.2%） | 0.988 / 4.2% | 0.985 / 18.7%（含 CPU，N=4） |
| a2a | 0.972 / 12.4% / 0.4% | 0.987 / 12.1% / 0.4% | 0.964 / 0.0% | 0.965 / 3.1% / 0.1% | 0.977 / 3.1% / 0.1% | 0.959 / 12.4% / 3.1% |
| mixed | 0.957 / 12.5% / 0.4% | 0.956 / 12.5% / 0.4% | 0.925 / 0.0% | 0.924 / 3.1% / 0.1% | 0.924 / 3.1% / 0.1% | 0.985 / 14.3%（含 CPU）/ 3.7% |

**重均衡时间**：在 1 µs 采样粒度下，所有故障都在下一个采样窗口内就进入新的稳态；远端感知延迟按 2 µs 建模。

**对照方案的典型问题**（全表见 `full_tables.md`）：
- spray 在 d2d 降 lane 故障下效率从 0.99 跌到 0.83：慢平面积压造成长尾。
- spray+dq2 在 d2d F3far 下受损设备损失 6.2%，是 1/N 的 2 倍；在 alltoall F3 下效率只有 0.72。
- ecmp 在 d2d F1 下受损设备损失 23%，ecmp+dq2 为 25%（1/N 为 12.5%）；ecmp+dq2 在 d2d F3far 下损失 10.1%（1/N 为 3.1%）。
- adaptive+caqm 在 alltoall 各故障下效率 0.81–0.90，在混跑下 0.67–0.82。
- static 在 h2d F3near 下损失 23%（1/N 为 6.2%）。

注意：d2dread 的端口隔离（F1、F4）对对照方案不可比。对照方案没有读请求上限，所有读请求在故障前就已经发出；在"优雅隔离"语义下，响应仍然从被隔离的口排空，所以表现为"零损失"。FlexSpray 因为有读上限，隔离确实生效。

### 5.3 消融（种子 1）

| 变体 | a2a F0 | a2a F3far | mixed F0 | mixed F4 | d2dread F3far |
|---|---|---|---|---|---|
| FlexSpray（完整） | 0.964 | 0.977 | 0.925 | 0.985 | 0.983 |
| 去掉 SprayCC | 0.966 | 0.971 | 0.924 | 0.986 | 0.953 |
| 去掉 TP-group fair share | 0.937 | 0.950 | **0.664** | 0.818 | 0.976 |
| 去掉分发等待（slack） | 0.956 | 0.936 | 0.897 | 0.985 | 0.979 |
| 交换机改为 hash spray | 0.964 | 0.954 | 0.926 | 0.985 | 0.987 |
| segment 改回 64 KB | 0.938 | 0.967 | 0.906 | 0.993 | 0.987 |

结论：
- 贡献最大的是端侧的流级公平仲裁和平面感知的分发（含等待和读上限）。
- SprayCC 的增益主要在远端降速（尤其读流量）。
- 在当前无阻塞 fabric 下，ADAPTIVE_RATE 相对 hash 喷洒只在远端降速的 alltoall 中有明显优势。

## 6. 仿真器问题与提速（"顺手修一下"部分）

**提速**，结果逐字节不变：黄金回归集为 scratch 下 24 个 case 加 2 个大型 alltoall，每次改动后都对比 runlog。

| case | 原始 | 现在（默认构建） | 静态 + LTO |
|---|---|---|---|
| 128-host alltoall | 18.9 s | 10.4 s（1.82×） | 8.6 s（2.2×） |
| 32-host alltoall | 16.0 s | 11.0 s（1.45×） | 8.0 s（2.0×） |

主要优化点：
- traffic 加载中的 O(N²) 查找：128-host 加载从约 5 s 降到 0.1 s；
- 逐包按名字查 GlobalValue；
- PortTrace 写路径；
- 分配器的 slot 计数与空 VL 扫描；
- 默认使用 HeapScheduler；
- 修正 `[summary]` 计时。

**发现并修复的既有 bug**：
1. **CAQM/DCQCN 释放后使用**：TP 释放时没有 Dispose 拥塞控制对象，挂起的定时器在已释放的内存上执行。用 ASan 定位，表现为 trace 文件里出现随机 NUL 字节。
2. **CAQM 死锁**：零 payload 的 TA 响应带 1 字节"调度进度"，发送端计入了这 1 字节，接收端从不确认，在途量泄漏，最终卡在 1 MTU 的窗口下限。
3. **分配器空包段错误**：TP 在仲裁时被选中，提交时已被 CC 限速，返回空包导致崩溃；现在改为释放授权并重新仲裁。
4. **`UbEgressQueue` 的 TypeId 未注册**：`MaxEgressBytes` 无法配置，`--ClassName` 查询会崩溃。
5. **CAQM credit 计数器**：负 double 转 uint64 属于未定义行为，结果依赖编译器（另一会话修复，`36809459`）。
6. **DCQCN pacing 死锁**：降速时会按比例放大"下一次允许发送时间"的欠债，升速时却不缩小。速率曾被砍到接近 1 bps 下限时欠下的债，在速率恢复到 400G 后仍然有效，TP 要等约 200 ms，期间在途为 0，没有任何事件能唤醒它。现在每次速率变化都双向折算（`e7b93dd2`）。
7. **CAQM 乱序 ACK 死锁**：ACK 跟随数据逐包喷洒，会乱序到达。过期的累计序号被当成最新值，已确认字节数倒退（大序号时还会被误判为 2³¹ 回绕），残留一个包的"幽灵在途"，窗口在 1 MTU 下限时永远发不出去。成对卡住的现象就是 A↔B 共用 TP 对造成的（`e7b93dd2`）。

第 6、7 两项导致原评测中 60 个基线 case 死锁。修复后这 60 个 case 全部完成，黄金回归逐字节不变；DCQCN 论文复现 100 ms 仍收敛到 20.25 / 19.60 Gbps。

**建模层面的发现**：同一 VL 上逐包轮询仲裁时，小 ACK 和满载数据共享输出口，ACK 会被饿死（实测排队 7 µs）。所以新增 `ResponseVl` 选项，实验中所有方案统一开启。

**分析脚本本身的问题**：最初带故障 case 的上限 LP 用二分加单纯形求解，加上线程过量订阅，490 个 case 耗时近 7 小时。改为单个 LP 加内点法、单线程多进程之后，只需 78 秒。

## 7. 局限与待办

- **对照方案死锁（已解决）**：原评测中 60 个基线 case 死锁，根因见第 6 节第 6、7 项，已修复并重跑全部 210 个 CC 基线 case，无一死锁。
- **故障语义是"优雅隔离"**：停止接纳新流量、排空在途流量。主机链路硬断导致的在途丢包，因为缺少 TA 级重发，暂不支持。另外，LP 假设被隔离的容量在 t_f 时刻立即为 0，因此隔离类故障下的效率略偏乐观；个别情况大于 1，例如 seg64 的 a2a F4。
- **规模**：本次为中等规模（48 端点、64 交换机、8 平面）。更大规模和非无阻塞 fabric（此时 ADAPTIVE_RATE 的价值预计更大）留待后续。
- **链路亚健康注入的支持范围**：`link_health.csv` 只支持单线程运行（不支持 MTP/MPI）。
