# FlexSpray：UB 多平面 Packet-Spray 负载均衡与拥塞控制 —— 当前版本报告（v5.3）

本文只描述当前版本。历史版本（v5.2、v5.1、v4）的报告在 `history/REPORT_round4_v5.2.md`；交付入口是 `DELIVERY.md`。

每条结论带有以下标签之一：

- **【已实现并验证】**：调参种子和未见种子上都成立；
- **【有限条件下成立】**：成立，但依赖文中写明的定义或条件；
- **【仍是假说】**：有机制性解释，但没有用实验确认；
- **【未解决】**。

- **代码**：分支 `feat/flexspray`，标签 `flexspray-v5.3`。比较基线是 `flexspray-v5.2`（不移动）。

- **方案组成**（每项后面的版本号是引入它的版本）：
  - 交换机：`ADAPTIVE_RATE` 平面内选路，TPG 公平份额只计可用成员（v3）；
  - 端点：
    - `MIN_DRAIN_TIME` 分发，严格等待（v4）；
    - 速率估计的应用受限保护（v5.1）；
    - SprayCC 边沿打标，组加性增量 15%/周期（v5.2）；
    - READ 请求走控制 VL，读响应豁免 CC 窗口（v3）；
    - **入口打标 READ 调度（v5.3）**；
  - 故障：本地端口断开立即判死；远端用 PROBE/PROBE_REPLY 检测（10 µs 静默 + 3 × 5 µs）；死 TP 的段重新派发 + replay fence；GBN 重传。
- **适用范围**：
  - 拓扑：4 台服务器 × 12 个设备，8 个平面，L1/L2 两级，400G；
  - 业务：RTP 的 URMA WRITE/READ，每个任务一个 Jetty；
  - 故障：单故障，包括优雅隔离、降 lane 到 3/4 和硬断链；
  - 不在范围内：原子操作重放、整组平面同时失效、TP 回收、更大规模（见 `TODO.md`）。

## 2. 评估口径

- 规则见 `EVAL_PROTOCOL.md`。
- 种子：
  - 调参用种子 1、2。前几轮已看过的种子 3–6 和 map 1、2 不算盲测。
  - **未见集**为种子 7、8 和 `--map 3`，在 v5.3 冻结（`0413d8ef`）之后才首次运行。
- **eff_fixed**（LP 效率）：方案无关的故障上限 / 实测 makespan。它大于 1 不代表超过最优。
- **逐设备利用率**：每个设备每个方向的全程协议利用率，取需求 ≥ 0.9 的方向中的最差值。
  - 窗口为 [该方向第一条流的释放时刻, 最后完成时刻]；
  - 业务字节只计一次（`util_biz`）。
  - 分析器修正对旧版和新版一致使用。
- **相对健康损失**：1 − makespan(F0) / makespan(故障)，按设备逐个计算（见第 6 节）。

## 4. 读混跑：机制、证据和敏感性

- **关键路径**：SSD0 只有平面 4/5，是 makespan 的瓶颈（需求 1.003）。v5.2 中，热点读者的 a2a READ 响应和 KV 响应在读者平面 4/5 的入口相遇，L1 下行口形成 400–780 KB 的常驻队列。
  - 156 µs 时，读者其余 6 个平面已经空闲，平面 4/5 还需 12–15.6 µs 排空。这部分已进入交换机，无法改道。
  - 最差响应方需要提前约 2.1 µs 完成（173.1 → 171.0 µs），才能达到 0.90。
- **机制**（`ReadIngressMarkWeight`）：
  - 请求方对每个本地端口维护最近收到的 READ 响应中被 SprayCC 边沿打标的比例（EWMA，增益 1/32），对应自己在该平面入口的排队。
  - `MIN_DRAIN_TIME` 为 READ 请求打分时，乘以 (1 + 0.3 × 打标比例)。
  - 信息全部来自端点自己收到的报文（网络头中的 FECN 位），不新增字段，不使用全局信息。
  - 只改变"请求发往哪个平面"，不改变"请求多少"。这与已否定的"按标记收缩读预算的 AIMD"不同。
  - 只能走平面 4/5 的 SSD 流量，两个成员受到同样的惩罚，所以不受影响。
- **证据**（`fig/t11_tail_v52_v53.png`，同一 case 种子 1）：v5.2 中读者的平面 4/5 和 SSD0 拖尾到约 172 µs；v5.3 中所有平面约在 168 µs 一起结束。
  - 未见种子 7、8 上（关闭 → 开启）：
    - SSD0 发送利用率 0.932–0.996 → 0.990–0.996；
    - 最差读者收利用率 0.899 / 0.917 → 0.933 / 0.968；
    - KV 读完成时间 169–175 → 161–165 µs；
    - 非读者 a2a 最晚完成 ≤ 174 → ≤ 167 µs；
    - 浅缓冲下交换机阻塞相同（1.2–1.4%），队列峰值略低（812–842 KB，关闭时为 874–914 KB）。
  - 没有把代价转移给其他业务。
- **敏感性**（mixedread 逐设备）：

| 权重 | 0 | 0.15 | 0.3 | 0.5 | 1 | 4 | 16 |
|---|---|---|---|---|---|---|---|
| 种子 1 | 0.889 | — | 0.927 | — | 0.894 | 0.868 | 0.854 |
| 种子 1、2 最差 | 0.889 | 0.921 | 0.927 | 0.910 | — | — | — |

  - 权重在种子 1 上选定。在 0.15–0.5 范围内都 ≥ 0.91；权重 ≥ 1 时，a2a 被过度推离平面 4/5，响应方平面 4/5 的发送口空闲，结果变差。
  - 所以本机制是**有界的偏置**，不是闭环控制，标为"有限条件下成立"。
  - 其他负载与拓扑下的权重适用性尚未验证。
- **本轮否定的原型**：权重 4 和 16（过度转移，见上表）。前几轮已否定的方法见 `history/`。

## 5. 正确性审计（第五轮）

| 检查项 | 结果 | 标签 |
|---|---|---|
| T14：同一 Jetty 上多个无序 WQE 交错 | **证实**：窗口 2，WQE 为 8/4/4 段时，B 拿到 TaSsn 1，A 占据 2..8；TaSsn 4 被确认时 B 即被报告 COMPLETED，而它 4 段中有 3 段从未被接纳（256 B 中 192 B 静默丢失）。<br>**修复**：WQE 只有在全部字节都已接纳、且自己最后一个接纳的 TaSsn 已被确认时才完成；若 COMPLETED 的 WQE 还有未发段要取消，直接中止。<br>**测试**：4 种交错模式，旧代码失败、新代码通过。<br>**影响范围**：FlexSpray 矩阵不受影响（RTP 每个任务一个 task-scoped Jetty），已在 `ub-app.cc` 核实 | 已实现并验证 |
| replay fence：被封 TP 对上的其他工作 | **发现活性缺陷**：误判死亡（1/64 降速）后，目标端自己的 WRITE 在该 TP 对上已收到传输层 ACK，但 TAACK 只能经由已死的对端 TP 返回，于是永远等待；该 TP 没有在途传输工作，检测器不会触发。<br>**修复**：收到 fence 即判本地这一端的 TP 也已死亡，其等待中的工作重新派发，反方向也随之被 fence。<br>`fence_false_death_bidir`：30 ms 时 2 个任务挂起 → 0 个，P1–P6 通过 | 已实现并验证 |
| fence 的作用方式 | 只携带在重发段上：4 B 的请求头扩展（被取代的 TPN，仿真中用 tag 表示，未计入包长；开销 ≤ 重发包数 × 4 B）。<br>目标端由**收到的报文**驱动本地状态（在接收 TP 上调用 `FenceInboundTp`），不由仿真器修改远端状态 | 已实现并验证 |
| 迟到的 ACK / 读响应、TP 复用 | 迟到的响应按记录中当前那一代 TP 的身份校验，否则丢弃。<br>fence 以 TPN 为键：前提是死 TP 永不回收（当前实现如此）。若引入 TP 回收，fence tag 需要加入代号 | 有限条件下成立 |
| 完成语义 | 段和任务只完成一次；完成时已执行；覆盖完整；按依赖排序的最后写者正确；完成后不再执行；活端口的 credit 守恒。22 个恢复用例（`flexspray_regress.py`），全部通过 | 已实现并验证 |
| **远端执行恰好一次** | **不成立**：重发会重复执行（每个用例 0–12 段）；WRITE/READ 在内容相同的前提下是幂等的 | 已实现并验证（否定结论） |
| 原子操作；整组平面失效 | 原子操作不重发；整组失效时 WQE 被拒绝 | 范围之外 |
| 修复的代价 | 硬断链 128 个 case：全部完成，67 个逐位相同，最差值不变（0.932）。<br>a2a H4 −1.2 pp（4 个种子），mixed H4 s6 −1.2 pp，H4p4 s1 −1.1 pp，mixedread H1far s5 +1.8 pp。<br>fence 取代了 25 µs 的远端检测（没有探测和 RTO，丢失字节 5.2 → 2.4 MB），但 a2a H4 仍变慢，原因未查明 | 仍是假说（T17） |

**结论**：在当前支持的范围内，没有遗留的提前完成、完成后执行或数据遗漏缺陷。

**解读**：
- **按每个设备自身的 N**，判定为**不满足**。损失 ≥ 1/N 的行全部是 8 平面 NPU，出现在以下几类故障中：
  - F1far / H1far 的 h2d：NPU 的对端是 4 平面 CPU；
  - F4 / H4：整个 L1 平面，同服务器的 CPU 只有 4 个平面；
  - F4p4 / H4p4：NPU 的流量受 SSD0 限制，SSD0 丢掉 2 个平面中的 1 个。
- 这些行中，**每一行**在同一故障下，流体 LP 最优解的网络层面损失（1 − T_ideal(F0) / T_ideal_fixed(故障)）同样 ≥ 1/N。说明超出部分来自异构对端的容量约束，而不是方案的额外损失。
  - 这里比较的是网络层面的 LP；逐设备的 LP 没有计算。
- **按受损设备中最小的 N**：h2d F1far / H1far **不满足**（唯一受损设备是 NPU6，N = 8，损失 0.187）；其余结构满足。这只是待确认的口径（第七轮修正，见 FEASIBILITY §0）。
- 原题是"<"，这里报告的是"≤"。
- 在**降 lane**（F3*）中，每个设备的损失都小于自身的 1/N。但有 4 个 NPU 行超过了"移除容量 + 0.5 pp"：h2d F3far 种子 7、8，损失 4.5%，移除 3.1%。原因没有单独分析。

## 9e. 第十轮补充（默认配置仍为 v5.3）

**评价口径**：
- 单故障损失并列报告原文 < 1/N_dev 与工程门槛 k/(4·N_dev) + 0.5 pp；N_dev 是受损设备自己的平面数（第九轮对 CPU 的计算有误）；
- 物理可行性用逐设备截止时间 LP 判定（`flexspray_devgate_lp.py`）。

**机制**（默认关闭）：`PortCommitDelay`（端口承诺的排空时间上限）、`ServiceTimeScore`（统一的完成时间估计）、`ServiceResidual`（发送后残差，带 Karn 规则和衰减）。

**结果**：
- 候选 S4 在写方向的所有降 lane 档位都通过；
- 读方向相对 M 有回退；
- lane 行门槛通过数高于 M 和 B1（主矩阵 33/42，未见集 36/56）；
- 不满足 1 pp 保护条件，因此不进默认。

见 FEASIBILITY §8。
